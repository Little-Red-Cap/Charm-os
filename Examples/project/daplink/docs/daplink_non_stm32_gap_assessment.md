# DAPLink 非 STM32 端口缺口评估

这份文档回答一个更狠、也更接近未来的问题：

如果第四个端口不再是 `STM32`，而是例如 `ESP32`、`RP2040`、`GD32` 这类平台，
当前 `Examples/project/daplink` 的边界能不能扛住？

## 结论先说

当前这套结构已经能比较稳地支撑：

- 新增更多 `STM32` 端口
- 在不污染 `app/` 的前提下继续扩展 `STM32 family`

但它还不能直接证明自己已经是“一套彻底平台无关的 DAPLink 平台”。

更准确的判断是：

- 对 `STM32` 家族横向扩展：已经进入可复用状态
- 对非 `STM32` 平台扩展：边界已经出现，但还需要补平台契约与 backend 实现面

## 当前已经站稳的层

### `app/`

这里已经基本满足“新增芯片不应改这里”的要求：

- `CMSIS-DAP` 协议
- DAP transport / 调度
- CDC bridge policy
- runtime / queue / policy

这些模块当前不直接依赖具体 MCU 寄存器名，也不要求知道 HAL 句柄名。

如果未来加 `ESP32`，理论上 `app/` 不应成为主要改动面。

### `frontends/usb/`

这里负责“主机如何看到 DAPLink”。

当前实现虽然主要跑在 STM32 USB backend 上，但设备模型和最小状态机本身已经是本项目自有能力。

这意味着：

- 如果未来还是 USB DAPLink，只需要补新的 USB backend glue
- 如果未来变成无线 DAPLink，则优先扩展 `frontends/`，而不是回写到 `app/`

### `f103 / g431 / h503`

这三个目录已经证明了一件重要的事：

新增一个 `STM32` 端口时，工作可以主要落在：

- 端口目录
- `platform/stm32/`
- 少量 `port/` 公共 glue

而不是不断把 `#if defined(...)` 回写到主流程。

## 当前真正会顶到的层

### 1. `platform/stm32/` 仍然是主复用中心

这不是问题本身，但说明当前公共复用中心仍然建立在 `STM32` 事实上。

换句话说：

- 现在已经有“平台层”
- 但目前真正成熟的是 `platform/stm32/`
- 未来如果加 `ESP32`，就必须新增一个同等级的 `platform/esp32/`

这一步不是补一个文件就完，而是要补一整套平台桥接。

### 2. `port/` 的平台无关契约还需要继续打磨

当前 `port/` 已经比早期干净很多，但如果要接非 `STM32`，还要继续验证这些问题：

- 现有 `daplink::port::*` 契约是否真的只表达“能力”，而不暗含 STM32 语义
- `port_runtime`、`usb_config`、board/backend capability 是否足以覆盖非 STM32 平台
- 是否仍有少量默认前提来自当前 STM32 backend 的工作方式

这部分不是重写，而是继续做“契约压力测试”。

### 3. backend 与 USB 控制器 glue 需要新实现

如果换成 `ESP32`，最现实的新增工作不会在协议层，而会集中在：

- SWD GPIO bitbang backend
- reset / Hi-Z / pin direction 控制
- USB device controller backend，或改走其它前端链路
- UART / CDC 桥接接线
- 时钟、延时、tick、busy wait 等 runtime 能力

也就是说，真正的成本主要在平台实现层，而不是 `CMSIS-DAP` 本身。

## 如果未来要接 ESP32，理论上不该动的层

为了避免以后再次长成屎山，可以先把“不该动”的层写死：

- `app/`
  - 不该因为换平台而出现新的芯片条件分支
- `docs/` 里的分层契约
  - 不该一边移植一边回退边界
- 现有 `STM32` 端口目录
  - 不该为了适配 `ESP32` 被迫加入跨平台判断

如果未来真的发现必须大改这些层，优先说明的是契约没打稳，而不是“新平台太特殊”。

## 如果未来要接 ESP32，应该新增或加强的层

### 优先新增

- `platform/esp32/`
  - 提供与 `platform/stm32/` 对等的平台实现面
- `esp32/` 端口目录
  - 只保留板级事实与具体 SDK / toolchain 接线

### 优先加强

- `port/` 公共契约
  - 确认各能力是否足够中性
- `frontends/`
  - 评估未来是否仍只依赖 USB，还是要支持无线 / 网络前端
- `base/`、`io/`
  - 确认这些最小基础能力不会继续带出历史仓库语义

## 现实建议

如果短期目标仍然是把 `DAPLink` 先整理到可独立开源，当前最值得做的不是马上硬上 `ESP32`，
而是继续完成下面几件事：

1. 把 `STM32` 路线的边界彻底收稳
2. 让 `port/` 的平台无关契约更明确
3. 把未来非 `STM32` 端口需要满足的 platform contract 提前写出来

这样等我们真加 `ESP32` 时，新增的是平台实现，不是架构返工。

## 最后的判断

如果今天问“这条线适不适合以后加 `ESP32`”，我的答案会是：

- 适合继续往那个方向演进
- 但现在它仍然首先是一套 `STM32 DAPLink` 架构
- 真正的跨平台能力边界，下一阶段主要要在 `port/` 和 `platform/<vendor>/` 上继续打实
