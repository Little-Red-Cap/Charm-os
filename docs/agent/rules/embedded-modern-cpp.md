# Embedded Modern C++ Rules

用途：
- 定义 Charm 项目在现代 C++ 单片机开发中的核心技术立场。
- 约束 AI 不得默认回退到传统嵌入式 C/C++ 思维。
- 要求接口、抽象、组织方式优先服务于语义正确、可验证、零成本抽象与长期演进。

适用场景：
- 讨论接口设计、抽象设计、类型系统建模
- 判断某个实现是否错误回退到传统嵌入式写法
- 讨论是否应采用更现代、更强类型的方案
- 评估某个抽象是否符合零成本原则

不适用场景：
- Charm 项目内具体模块依赖、初始化装配、IO 纪律判断
- 单纯的协作风格问题
- 某个技能的任务步骤定义

相关文件：
- `collaboration.md`
- `charm-architecture.md`

---

# 1. 项目定位

本项目默认面向以下运行环境：

- Bare-metal 或最小化运行时
- 无依赖动态内存分配的运行时
- 不依赖异常
- 不依赖 RTTI

默认约束包括：

- 资源受限
- 性能敏感
- 强调实时性、功耗与响应延迟

---

# 2. 世界观声明

AI 在本项目中应默认接受以下立场：

本项目不以以下目标为优先：

- C 兼容性
- ABI 稳定性
- 旧编译器支持
- “更多人都能轻易接受”

默认目标语言为：

- C++23
- C++26

默认组织方式为：

- C++ Modules

项目唯一目标应优先理解为：

- 语义正确
- 可验证
- 零成本抽象
- 可长期演进

当“传统写法”与“更现代、更强类型、更可组合、更偏编译期建模的写法”冲突时，原则上优先后者。

---

# 3. 硬性禁止项

以下内容在本项目中默认视为设计失败：

- 动态内存分配：`new` / `delete` / `malloc` / `free`
- 异常
- RTTI
- 用宏承担语义职责
- 用运行期分支模拟编译期选择
- 协议层 busy-spin
- 协议层阻塞等待
- 协议层自定义超时循环
- 协议层直接依赖 platform / hal / driver
- 手写入口初始化顺序

若任务涉及这些内容，AI 应优先尝试寻找符合项目立场的替代方案。

---

# 4. 强烈不推荐项

以下内容应尽量避免，使用时必须能清晰说明理由：

- `void*`
- 裸语义指针作为接口参数
- 把 `.h / .cpp` 拆分作为默认结构
- 通过注释补足类型缺失的语义
- 通过调用顺序或约定隐式传递语义

优先替代方式包括：

- 强类型
- 值语义句柄
- `std::span`
- `std::array`
- `std::optional`
- `std::expected`
- tag type
- `concept + template`
- `constexpr / consteval`

---

# 5. 接口与建模原则

## 5.1 类型系统优先
如果一个接口需要依赖文档才能安全使用，则其类型设计大概率存在问题。

接口设计优先级应大致为：

1. 强类型
2. 值语义句柄
3. 标准容器视图
4. 显式可选与错误建模

## 5.2 Domain 优先
应先建模“是什么”，再建模“怎么做”。

- 行为是 domain 的投影
- 数据结构先于算法
- 接口应表达语义，而不是调用步骤

## 5.3 编译期优先
能在编译期解决的问题，不应拖到运行期。

鼓励：

- `constexpr`
- `consteval`
- 类型级状态机
- 能力注入
- 编译期配置

---

# 6. 零成本抽象原则

任何抽象都应能够回答以下问题：

1. 会增加多少 Flash 占用？
2. 会增加多少 RAM 占用？
3. 会增加多少运行期开销？
4. 编译器能否完全裁剪或优化？

若无法解释成本，就不应轻易引入抽象。

---

# 7. 激进优先，但拒绝炫技

当“更现代但更激进”与“更传统但更熟悉”冲突时，默认应优先现代方案。

但要区分：

- 激进：用类型系统表达更强约束
- 炫技：为了使用新特性而使用新特性

AI 不应把语言新特性本身当成目标，目标始终是：

- 语义正确
- 可验证
- 零成本
- 可演进

---

# 8. 逃生舱口原则

本项目允许有限妥协，但妥协必须满足以下约束：

- 有明确理由
- 范围最小化
- 隔离在边界处
- 有明确标记
- 有文档说明
- 可定期复审

合理理由通常仅限于：

- 硬件强制约束
- 第三方库 / SDK 强制接口
- benchmark 证明的性能关键路径

AI 在建议妥协方案时，应同时说明：

- 为什么不能使用规范方案
- 妥协范围有多大
- 如何隔离
- 如何标记
- 后续是否可移除

---

# 9. 评审时的默认判断

在评审或生成代码时，AI 应默认检查：

- 是否错误引入动态分配
- 是否错误引入异常 / RTTI
- 是否用运行期分支代替编译期选择
- 是否把语义塞进注释而不是类型
- 是否引入了不必要的脏接口
- 是否因为“易懂”而主动降低设计质量

---
