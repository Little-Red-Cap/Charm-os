# architect-review

用途：
- 用于 Charm 项目中的架构评审、设计评审、模块边界评估与演进方向判断。
- 帮助 AI 在面对跨模块、跨层级、跨能力链路的问题时，优先从结构、边界、演进性与一致性出发做判断。

在这些场景使用：
- 讨论某个模块是否应该存在
- 讨论某个能力应放在哪一层
- 评估某个改动是否破坏整体架构
- 比较多个设计方案的长期演进质量
- 评审初始化、能力装配、IO 路径、错误模型等系统性问题

不要用于：
- 单纯 review 某个小函数的语法或局部实现
- 从零直接写完整代码
- 替代项目级 rules 文件
- 只讨论沟通风格而不涉及结构问题

依赖规则：
- `../../rules/collaboration.md`
- `../../rules/embedded-modern-cpp.md`
- `../../rules/charm-architecture.md`

相关文件：
- `../code-review/SKILL.md`
- `../code-review/checklist.md`

# 1. 目标

本技能的目标是帮助 AI 回答这类问题：

- 这个设计是否符合 Charm 的整体方向？
- 这个能力应该放在哪一层？
- 这个抽象是在增强系统，还是在污染系统？
- 这个改动是短期方便，还是长期退化？

评审重点不是“能不能实现”，而是：

- 是否值得这样实现
- 是否应该这样组织
- 是否会破坏长期演进能力

---

# 2. 评审视角

架构评审默认使用以下视角：

## 2.1 分层视角
先判断改动落在哪一层：

- Foundation
- Runtime
- IO
- Domain

再判断它是否破坏依赖方向。

## 2.2 装配视角
判断该能力应通过哪种方式进入系统：

- `init.graph`
- `CoreSystemChain`
- `BoardChain`
- `extra nodes`
- RuntimeContext / capability 注入

不应接受“先能跑起来再说”的随意装配。

## 2.3 边界视角
判断是否存在：

- 跨层泄漏
- 内部细节外露
- 脏接口外扩
- 平台细节污染核心模块
- 适配层和核心逻辑边界不清

## 2.4 演进视角
判断设计是否：

- 可持续扩展
- 可替换
- 可验证
- 成本清晰
- 不因局部方便而牺牲全局一致性

---

# 3. 评审流程

## 3.1 先识别改动类型
先判断当前问题属于：

- 局部模块设计
- 跨模块能力流转
- 初始化链路调整
- IO 通道模型变化
- 错误模型变化
- 时间源与能力注入变化
- 第三方依赖接入
- 平台边界接入

## 3.2 先看是否破坏硬边界
优先检查：

- 是否破坏分层依赖
- 是否绕过统一装配路径
- 是否绕过统一错误模型
- 是否绕过统一时间源
- 是否在协议层引入不允许的等待模型
- 是否把平台/SDK 细节直接扩散到核心逻辑

## 3.3 再比较方案质量
若多个方案都能做，应比较：

- 哪个更符合 Charm 的长期方向
- 哪个更强类型
- 哪个更容易验证
- 哪个更能保持系统一致性
- 哪个更少制造后续债务

## 3.4 最后给出建议落点
输出不应停留在抽象评价，应尽量给出：

- 推荐放在哪一层
- 推荐通过什么能力注入/装配
- 哪些边界必须保留
- 哪些地方必须隔离
- 哪些地方可以允许有限妥协

---

# 4. 默认结论组织方式

架构评审建议按以下结构输出：

## 4.1 当前问题是什么
先明确当前在讨论的是：

- 能力归属问题
- 依赖方向问题
- 初始化装配问题
- 核心抽象问题
- 适配层边界问题

## 4.2 关键判断
说明当前判断依据，例如：

- 违反了哪个层次边界
- 破坏了哪条项目纪律
- 与哪条长期技术立场冲突
- 会导致什么后续复杂性

## 4.3 推荐方案
给出推荐结构，并说明：

- 为什么放在这一层
- 为什么不放到别处
- 为什么这个边界比其它方案更稳

## 4.4 不推荐方案
若有常见但不合适的做法，应直接说明为何不推荐。

---

# 5. 默认偏好

架构评审时，AI 应默认偏好：

- 清晰分层
- 统一装配
- 统一错误模型
- 统一时间源
- 边界隔离
- 编译期建模优先
- 最小必要妥协
- 第三方脏接口仅停留在边界层

不应偏好：

- 图省事的跨层调用
- 临时挂载式装配
- “先跑通再重构”的常态化借口
- 把平台细节提前渗透到核心抽象中

---

# 6. 何时允许妥协

仅在以下情形下可讨论有限妥协：

- 硬件强制约束
- 第三方 SDK/C 接口限制
- benchmark 支撑的性能关键路径

即使妥协，也应：

- 限定范围
- 边界隔离
- 有清晰标记
- 有说明文档
- 不扩散到系统核心

---

# 7. 与 code-review 的区别

本技能关注：

- 结构
- 边界
- 层次
- 演进方向
- 系统一致性

而 `code-review` 更关注：

- 某段实现是否违规
- 某个 PR 是否存在阻断问题
- 某个具体接口是否退化

架构问题优先用本技能；实现问题优先用 `code-review`。

---

# 8. 与 rules 的关系

本技能只组织架构评审过程。

- 协作方式以 `collaboration.md` 为准
- 技术立场以 `embedded-modern-cpp.md` 为准
- 项目具体约束以 `charm-architecture.md` 为准

本技能不得覆盖这些规则。
