# Phase 2 Gap Map

本文件用于描述 Charm 在 Phase 2（收敛执行阶段）中的主要缺口。
目标不是重新发明架构，而是明确：

- 哪些地方仍然痛
- 哪些能力虽然可用但体验差
- 哪些能力要继续扩展
- 哪些路径要继续收敛
- 哪些历史包袱要清理

后续所有“大手术”，都应尽量对应到本文件中的缺口类别，而不是临场凭感觉扩散。

## 1. 仍处于痛点状态的部分

### 1.1 执行语义尚未完全统一

SSU 已经成为主线，但系统里仍有大量历史路径本质上依赖：

- event 投影
- 旧式推进逻辑
- 局部临时约定

这意味着系统虽然已经拥有统一语言，但还没有让所有高频路径真正以这套语言为第一表达。

### 1.2 纪律仍偏软约束

当前已经有：

- `ssu_submit_discipline.md`
- PR 模板
- review checklist

但这些仍主要属于“文档纪律”和“评审提醒”。
它们离“新增旁路很难自然长出来”还有距离。

### 1.3 样板数量仍不足以完全压制偶然性

严格模式样板已经开始具备复制性，但数量仍偏少。
现阶段还不足以证明：

- SSU 可以稳定吞下更多真实路径
- 不同触发形态都能落入同一主线
- 成功不是单个样板的偶然巧合

### 1.4 工具链/模块系统仍然有工程性阻力

当前已知问题包括：

- 某些编译器对分区模块不稳定
- 某些标准库组合（如 `span` / `array`）在模块语境下可能诱发 ICE
- 不同 target 的模块构建链表现不完全一致

这意味着架构收口不只是代码问题，也仍然受工具链成熟度影响。

### 1.5 样板运行体验不够工程化

部分样板已经能编译、能导出诊断，但：

- 运行退出路径不总是顺滑
- 调试输出路径仍偏 demo 风格
- 结果采集还不够自动化

这会降低样板作为“主线证据”的质量。

## 2. 能用但不好用的部分

### 2.1 SSU 观测面已成立，但尚未形成默认诊断工作流

当前已经具备：

- `EventSource.json`
- `SsuOverview.json`
- `SsuHotspots.json`
- `trace.json / trace.csv`

但它们更像“可用输出”，还不是“标准排障路径”。

### 2.2 run_loop 审计已开始，但还偏静态标签

`submit_projection` 已经接入 run loop / phase，
但它更偏审计标注，还没有完全变成行为约束和团队默认语言。

### 2.3 严格模式可开启，但还不够傻瓜化

现在 target 可以双侧开启：

- 可执行目标开启 `CHARM_KERNEL_REQUIRE_SSU_META=1`
- `Charm-os` 同时开启 `CHARM_KERNEL_REQUIRE_SSU_META=1`

但它仍然需要显式配置，还没有变成“默认模板工程姿势”。

### 2.4 迁移路径可走，但主线感还不够强

开发者已经能看懂如何把 task 迁入 SSU，
但“按 SSU 来写最顺手”这一点还没有完全建立。

## 3. 需要继续扩展的能力

### 3.1 严格模式样板覆盖面

继续建立更多低噪声样板，优先覆盖：

- reactor/pump
- timer/service loop
- demand 驱动
- phase/run loop

目标不是凑数量，而是建立“不同触发语义都可复制”的证据链。

### 3.2 SSU 观测能力

当前观测面下一步应回答更实际的问题：

- 谁是 dominant submit
- 哪些路径长期 low-demand-share
- 哪些任务未声明 SSU 身份
- 哪些路径 budget 耗尽频繁
- 哪些路径持续 resubmit 成热点

### 3.3 配置化能力

像这次把 hotspots 阈值外置到 `KernelConfig` 就是正确方向。
后续仍需继续把“策略参数”从硬编码中抽出，形成：

- 默认值
- target 可覆写值
- 编译期校验

### 3.4 架构端检查能力

长期来看，仍要从“文档检查”推进到“工具检查”。
包括但不限于：

- lint
- 静态检查
- CI 审计项
- 构建期开关组合验证

## 4. 需要继续收敛的部分

### 4.1 新增执行路径的入口

所有新增执行协作，原则上都应优先落入：

- `event-submit`
- `io-ready-submit`
- `demand-submit`

如果不能落入，必须解释原因和回收路径。

### 4.2 app / system / platform 边界

虽然入口层已经显著收口，
但后续仍要避免：

- `app_system` 重新变成超级 main
- platform glue 倒灌回上层编排层
- 目标代码继续直接跨层操作底层

### 4.3 run_loop / phase 心智模型

run loop 不应只是“阶段回调表”，
而应逐步纳入 SSU 语言体系，成为：

- 可审计
- 可投影
- 可解释

的执行主线组成部分。

### 4.4 历史 event-only 思维

很多旧路径仍停留在“先发个 event 再说”。
后续要逐步收敛成：

- 先辨识触发语义
- 再决定 submit 路径
- 再决定 budget / blocking / ownership

## 5. 需要清理的部分

### 5.1 历史旁路与临时推进逻辑

凡是不属于主 submit 三分法的路径，都应进入台账，逐步清理。

### 5.2 样板中的临时手术痕迹

为了验证而加入的：

- 手工限次循环
- demo 风格直接打印
- 临时兜底逻辑

后续要明确区分：

- 哪些是长期保留的诊断入口
- 哪些只是阶段性验证工具

### 5.3 构建与目录噪音

构建目录、副产物、临时运行文件、target 特例配置，仍要继续清理。
目标是：主线判断不被无关噪音淹没。

### 5.4 文档重复与入口分散

SSU 文档已逐渐增多，后续需要择机做一次轻量去重，避免出现：

- 每篇都对
- 但入口过多
- 维护成本上升

## 6. 当前阶段的总判断

Charm 当前最大的挑战，不再是“有没有架构主线”，
而是：

> 架构主线已经成立，但默认工程行为还没有完全服从它。

所以 Phase 2 的关键，不是继续发明新概念，而是：

- 扩展能说明问题的能力
- 收敛新增路径
- 清理历史旁路
- 让正确姿势越来越像默认姿势

## 7. 后续大手术的原则

后续如果要动“大手术”，建议遵守以下原则：

1. 优先切历史旁路，不先打碎已稳定主线
2. 优先切默认路径，不先优化边角体验
3. 优先切执行语义入口，不先切局部实现细节
4. 每次手术都要能明确对应本文件中的某一类缺口
5. 所有大手术都要能回到：是否让系统更难绕开主线
- 当前进展：run_loop 已从字符串 submit 标签升级为强类型 `SubmitProjection`，并要求 `add_step(...)` 显式声明 submit 语义。
