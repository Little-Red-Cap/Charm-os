# Charm Agent Glossary

本文件用于统一 Charm 项目中常见术语的理解。  
目标不是给出百科定义，而是帮助 AI 在协作、代码生成、代码审查、架构评审中保持稳定语义。

使用原则：
- 优先使用本项目语境中的含义
- 不要用外部通用概念替代项目内概念
- 若术语在当前上下文中仍不明确，应明确说明“不足以确认具体含义”

---

# 1. Agent
在本目录语境下，Agent 指能够在 Charm 项目中读取规则、选择技能、组织任务执行方式的 AI 协作主体。

它不是单纯的大语言模型输出，而是：
- 受规则约束
- 按任务选择技能
- 使用统一模板组织输出
- 在 Charm 项目语境下工作的协作实体

---

# 2. Rules
Rules 指长期稳定、跨任务生效的约束文件。

它们定义：
- 如何协作
- 采用什么技术立场
- 遵守什么工程边界

Rules 回答的问题是：

> “在 Charm 中，AI 应该遵守什么？”

---

# 3. Skills
Skills 指面向具体任务的工作说明。

它们定义：
- 某类任务应如何展开
- 应优先检查哪些维度
- 输出应如何组织

Skills 回答的问题是：

> “在 Charm 中，AI 遇到这类任务时应怎样工作？”

---

# 4. Prompt
Prompt 指当前任务的直接请求内容。  
它是一次任务的输入，不等于长期规则，也不等于技能。

Prompt 回答的问题是：

> “这次要做什么？”

---

# 5. Session
Session 指当前对话或当前任务的运行上下文。

它通常包含：
- 当前问题
- 已确认约束
- 已加载规则
- 已选择技能
- 当前仍未确定的点

Session 不是长期配置仓库，而是运行时状态容器。

---

# 6. `init.graph`
`init.graph` 是 Charm 中统一初始化装配路径的核心表达。

在 Charm 语境下，它意味着：
- 初始化顺序不应手写散落在入口
- 初始化关系应被结构化表达
- 初始化本身属于架构的一部分，而不是临时细节

当讨论初始化方案时，默认应优先回到 `init.graph` 体系内，而不是接受入口手写顺序。

---

# 7. `CoreSystemChain`
`CoreSystemChain` 指系统核心底座能力所在的统一装配链。

在 Charm 语境下，通常意味着：
- 核心系统能力应进入统一核心链
- 这类能力不应作为随意拼接的局部节点散落
- 它对应的是“底座级能力”，而不是上层应用逻辑

如果某能力属于系统底座，应优先考虑是否属于 `CoreSystemChain`，而不是进入 `extra nodes`。

---

# 8. `BoardChain`
`BoardChain` 指板级能力装配链。

在 Charm 语境下，通常意味着：
- 与板级硬件能力相关的能力应优先放入这里
- 板级 bringup、硬件资源描述、特定平台能力更适合在这一层完成注入
- 它与核心底座能力有别，不应随意混用

---

# 9. `extra nodes`
`extra nodes` 指额外装配节点区域。

在 Charm 语境下，它不是“任何东西都能塞进去的兜底区”，而是：
- 主要用于服务类、应用类节点
- 不应用来承载底座能力
- 不应用来绕开统一装配纪律

如果一个能力本应进入 `CoreSystemChain` 或 `BoardChain`，则不应图省事塞进 `extra nodes`。

---

# 10. `io::Channel`
`io::Channel` 是 Charm 中 IO 通道抽象的核心接口之一。

在当前项目语境下，至少应默认理解为：
- `read/write` 必须非阻塞
- 不应返回 `Ok(0)`
- 资源暂不可用时应返回 `Errc::would_block`

它不是“任意同步读写接口”的别名，而是带有明确项目纪律的通道抽象。

---

# 11. `io.reactor`
`io.reactor` 指统一的 IO 等待与调度机制之一。

在 Charm 语境下，它意味着：
- 协议层不应自行做 busy-spin / sleep / 阻塞等待
- 等待与超时应回到统一机制中
- IO 的可等待性与事件驱动不应散落在协议层里各写一套

---

# 12. `io.registry`
`io.registry` 指统一的通道/能力获取入口之一。

在 Charm 语境下，它意味着：
- 通道获取应优先走统一注册表或统一注入路径
- 默认通道已移除
- 不应依赖隐式全局默认对象
- 不应为了方便绕开 registry 直接乱拿底层对象

---

# 13. RuntimeContext
RuntimeContext 指运行时上下文中的统一注入/获取机制之一。

在 Charm 语境下，它通常意味着：
- 某些能力不应被模块内部偷取
- 应通过上下文显式注入
- 它是一种边界清晰的能力获取方式，而不是任意全局访问口

---

# 14. `util::Errc`
`util::Errc` 是 Charm 项目中的统一错误码模型。

在 Charm 语境下，它意味着：
- 错误码表达应尽量统一
- 不应每个模块都自建风格不同的错误枚举而导致语义分裂
- 它是跨模块、跨能力边界保持一致性的基础之一

---

# 15. `util::Result<T>`
`util::Result<T>` 是 Charm 项目中的统一结果类型。

在 Charm 语境下，它意味着：
- 正常值与错误值应通过统一结果模型表达
- 不应为了“简单”回退成 `bool` 或随意丢失错误上下文
- 上层应能基于统一模型理解失败原因与处理路径

---

# 16. `input.service`
`input.service` 指统一的输入采样/输入服务路径。

在 Charm 语境下，它意味着：
- 输入采样应通过服务层完成
- 业务层不应直接轮询硬件
- 输入相关能力应保持统一收口，而不是每个业务模块各自直接碰 HAL

---

# 17. `charm.system.clock`
`charm.system.clock` 指 Charm 项目的统一时间源。

在 Charm 语境下，它意味着：
- 业务、协议、驱动不应自建 `now_ms/now_us`
- 时间获取应通过统一 clock 能力注入
- 时间源统一是系统一致性的一部分，不是实现偏好问题

---

# 18. Capability
Capability 指一种被明确暴露、可注入、可约束边界的能力表达方式。

在 Charm 语境下，它通常意味着：
- 能力应被显式建模，而不是隐式偷取
- 能力边界应稳定清晰
- 能力注入优于全局乱取
- capability 不应退化成“什么都能塞进去的大袋子”

---

# 19. Escape Hatch
Escape Hatch 指在明确约束下允许的有限妥协。

在 Charm 语境下，它通常只应出现在：
- 硬件强制约束
- 第三方 SDK / C 接口限制
- benchmark 证明的性能关键路径

并且必须满足：
- 范围最小化
- 边界隔离
- 有注释标记
- 有说明文档
- 可定期复审

Escape Hatch 是受控例外，不是常规工程方式。

---

# 20. Non-blocking
Non-blocking 在 Charm 项目中不只是“函数不会睡眠”。

它更具体地意味着：
- 不进行阻塞等待
- 不做 busy-spin
- 不通过内部循环硬等资源
- 无资源时应显式返回上层可处理的状态，例如 `Errc::would_block`

它是一种系统级 IO/协议纪律，而不是单个函数实现细节。
