# Player UI 设计要求清单（对齐 PixelPlayer）

本文件不再只记录“风格印象”，而是作为 `app-vivid-MaterialDesign3` 的 **可执行设计要求清单**。

目标是避免协作时陷入：
- 图标再大一点
- 颜色再深一点
- 圆角再圆一点

后续所有 UI 调整，优先以本页的要求项为依据，再讨论是否要改目标本身。

---

## 1. 文档目标

本页用于回答 4 个问题：
- 我们到底要“像” PixelPlayer 到什么程度
- 当前 Player UI 哪些部分已经对齐，哪些还没对齐
- 下一步改动应该优先改什么，而不是凭感觉微调什么
- 哪些要求是视觉要求，哪些要求是结构要求，哪些要求是交互要求

本页结合以下来源整理：
- `Draft/Charm-os Player 仿 PixelPlayer 的可执行设计规范与代码改进建议.md`
- `Draft/PixelPlayer` 源码与组件实现
- 当前工程 `Examples/project/player/app-vivid-MaterialDesign3`

## 2. 总体设计目标

### 2.1 视觉目标
- 深色基底，不走高对比硬边工业风
- 强调柔和、厚实、带层次的 Material 3 Expressive 观感
- 大圆角、低对比边框、浅层阴影同时存在
- 强调色优先来自封面主题色，但必须保证可读性

### 2.2 结构目标
- 页面不是“控件堆叠”，而是清晰的区块组合
- 每个页面必须存在明确主视觉区和辅助信息区
- 顶栏、路径条、信息标签、列表卡片等模式应保持一致语法

### 2.3 交互目标
- 可点击元素优先保证命中面积，而不是只追求视觉小巧
- 页面切换、播放控制、列表操作要有清晰状态反馈
- 减少“看起来很炫但不能沉淀为系统能力”的特例样式

---

## 3. 我们当前对 PixelPlayer 的对齐范围

当前对齐的不是“1:1 临摹 Android Compose 代码”，而是以下 4 层：

- 页面信息架构
- 视觉 Token 方向
- 关键组合层模式
- 交互与状态表达方式

明确不做的事情：
- 不追求把 PixelPlayer 每一个像素直接搬到 `480x960`
- 不追求把 Android 特有的 Compose 动效全部照搬
- 不追求为了模仿而牺牲 `Vivid` 的可沉淀性

---

## 4. 页面级目标

### 4.1 Home

#### 必须具备
- 强对比 Hero 标题：主标题远大于副标题
- 封面拼贴是首页主视觉，不是附属插图
- 顶部操作区保持轻量，不能抢 Hero 标题视觉中心
- 首页内容区要体现“推荐 / 最近播放 / 统计”三类信息层次

#### 当前对齐判断
- 已有 `HeroTitle + HeroSubtitle`
- 已有封面拼贴与统计卡片
- 已有顶栏右侧双按钮
- 仍需继续提升首页各区块的视觉节奏差异

#### 具体要求
- Hero 标题继续保留显式大字号逃逸层，目前基准保持 `72px`
- 副标题必须明显小于 Hero 标题，并保持低强调色
- 顶栏按钮尺寸优先服务点击面积，不允许为了“更秀气”而压到难点
- 统计卡片要像“信息块”，不能像普通列表项

#### 量化规格（当前目标）
- Hero 主标题：`72px`，粗体，左右两行视觉节奏必须稳定
- Hero 副标题：`18px`，常规字重，颜色低于主标题强调级
- 顶栏按钮框：约 `40px`
- 顶栏图标：约 `14px`
- Hero 播放按钮：约 `78px`
- Hero 播放图标：约 `28px`
- 首页统计卡片高度：约 `76px`
- 首页区块主节奏：优先围绕 `24px` 级别大间距建立

#### 未来动效占位（暂不实现）
- Hero 标题进入时允许轻微淡入，不做大幅位移动画
- 封面拼贴可预留轻微浮起/层次变化，但不做复杂连续动画
- Hero 播放按钮未来允许做轻微按压反馈与阴影变化

### 4.2 Now Playing

#### 必须具备
- 顶栏结构明确：返回 / 标题 / 操作
- 封面是页面绝对主视觉核心
- 标题、作者、进度条、时间、控制区必须形成稳定纵向节奏
- 时间信息与标签信息要形成一行独立信息带

#### 当前对齐判断
- 顶栏与主结构已基本具备
- 进度条和信息带结构已具雏形
- 后续重点不再是“有没有”，而是“节奏和强调是否准确”

#### 具体要求
- 顶栏不能喧宾夺主，信息密度要低于正文区
- 标题行居中，但不能太贴近封面
- 时间行左/中/右三段必须稳定，不允许因为文案变化频繁跳动
- 进度条优先体现“可拖拽 + 有生命感”，不是单纯直条

#### 量化规格（当前目标）
- 顶栏按钮框：约 `40px`
- 顶栏返回图标：约 `20px`
- 顶栏更多图标：约 `14px`
- 标题文本框高度：约 `24px`
- 控制区侧按钮：约 `96px`
- 控制区主播放按钮：约 `116px`
- 控制区按钮间距：约 `14px`
- 时间行左右时间槽宽：约 `52px`
- 时间行中央信息槽最小宽度：约 `170px`
- 时间行内部主要节奏：约 `16px`
- 时间信息带圆角：约 `18px`
- 信息标签圆角：约 `12px`
- 进度条后续风格目标：厚度接近 `5dp` 量级、Thumb 半径接近 `8dp` 量级、应具备波形/生命感潜力

#### 未来动效占位（暂不实现）
- 顶栏切页时不做大位移，只允许短时淡入或轻微过渡
- 封面、标题、进度条未来可做分层进入，但必须支持 reduce-motion
- 时间信息带未来可增加轻微状态过渡，但不应造成布局跳动

### 4.3 Library

#### 必须具备
- 顶栏、Tab、路径条、列表卡片要形成清晰层级
- 路径条必须像“浏览上下文”，而不是普通按钮
- 列表项应强调封面、标题、辅助信息与操作入口的平衡
- Shuffle / Sort / Tabs 等工具区要统一为一类操作语言

#### 当前对齐判断
- 顶栏、Tab、路径条、列表卡片头都已成型
- 现在重点是继续统一列表项与工具区语言

#### 具体要求
- 路径条使用独立 pattern 处理，不再当作泛化 pill 拼接对待
- 列表标题与路径条之间要形成“内容块头部”关系
- 列表项封面尺寸、行高、信息层级要稳定，不要随页面局部试验频繁漂移

#### 列表项目标形态
- 列表项不能只被当成“图标 + 一行文字”的普通行
- 列表项至少应具备以下视觉分区：
  - 封面区
  - 主信息区（标题）
  - 辅助信息区（作者 / 专辑 / 状态）
  - 尾部操作或状态区
- 封面尺寸应形成稳定基准，当前参考 PixelPlayer 的 `56dp` 量级，不允许同页上下漂移
- 行高应围绕封面尺寸建立，不允许“为了看起来更松”而无规则拉高
- 当前播放项、选中项、普通项必须有可识别差异，但差异应来自统一语言，而不是临时加颜色/描边
- 尾部区域应保留未来接入更多操作或状态的空间，避免把全部宽度都挤给标题文本
- 列表项必须像“内容卡片中的歌曲条目”，而不是文件浏览器的普通文字行

#### 当前实现补充说明
- 当前 `Library` 列表项已经具备双层文本表达：主标题 + 副标题
- 当前 `Library` 列表项已经区分 `selected` 与 `current/active` 两种状态语义
- 当前播放项在非选中时也必须可识别，不能只有“选中后才像播放器列表”
- 当前无封面回退场景下，左侧图标应承担最小播放语义表达，允许使用 `play / pause` 指示
- 当前版本仍未实现尾部操作区，但必须继续保留尾部空间意识，不能把文本区无限扩张为全宽

#### 量化规格（当前目标）
- 顶栏按钮框：约 `40px`
- 顶栏图标：约 `14px`
- List Tab / Shuffle / Sort 这一族控件应共享接近的圆角和内部节奏
- 路径条文本高度：约 `16px`
- 路径条图标框：约 `24px`
- 路径条图标显示尺寸：约 `12px`
- 路径条圆角：约 `10px`
- 列表行高当前基线：约 `60px`
- 列表项封面目标基线：优先向 `56dp` 量级靠拢
- 列表项主标题必须明显强于辅助信息，但不能进入 Hero/Title 级强强调
- 列表项尾部状态/操作区应预留可视宽度，不允许主文本无限侵占

#### 未来动效占位（暂不实现）
- 当前播放项未来允许有轻微状态脉冲或 EQ 指示
- 选中项未来允许有容器或颜色渐变过渡
- 列表滚动本身不额外追求装饰性动画，优先保证稳定与可读

## 5. 视觉 Token 要求

### 5.1 颜色
- 主背景保持深色，但不要纯黑
- `primary` 用于当前播放、激活、重点强调
- `secondaryContainer / tertiaryContainer / surfaceVariant` 用于软性信息块与导航指示
- `onSurfaceVariant` 应主要承担次级说明文本，不承担主信息

### 5.2 圆角
- 顶栏按钮、路径条、信息标签、卡片都应偏大圆角
- 圆角不是装饰，而是统一设计语言的一部分
- 同一类组件的圆角不得随页面随意漂移

### 5.3 阴影与边框
- 阴影主要用于层次与浮起感，不用于制造强烈悬浮感
- 边框优先低对比细边框，不走硬描边风格
- 激活态优先用颜色、容器变化、轻阴影，不靠粗边框硬打出来

### 5.4 动效原则（预留）
- 当前阶段不主动实现复杂动效，但必须先定义未来边界
- 动效的职责是：强调层级变化、状态切换、可操作性
- 动效不应承担“补救结构不清晰”的职责
- 默认优先短时、轻量、低位移的过渡
- 必须预留 `reduce-motion` 路径：关闭位移/缩放，仅保留极短淡入或完全无动画

---

## 6. 排版要求

### 6.1 排版层级
- 当前建议至少保持 4 级：
  - Hero
  - Title
  - Body
  - Meta

### 6.2 当前实现约束
- `HeroTitle` 保留显式字体逃逸层
- 其余文本优先走 `font_role + weight`
- 页面侧继续通过 `PlayerTextRole` 做页面语义映射
- 通用 patch 生成统一走 `TextStyleSpec`

### 6.3 不允许的做法
- 同一种页面语义在不同页面随意换字号和字重
- 为了解决单点视觉问题，直接到页面里再塞一组新的裸 `FontId / FontWeight`
- 用颜色去代替层级，用加粗去代替结构

---

## 7. 组合层要求

当前我们已经验证，复杂 UI 不能只靠基础控件堆出来，必须通过组合层 pattern 约束。

### 7.1 已经稳定的组合层
- `TopBarLayout`
- `PathBarLayout`
- `ListCardHeaderLayout`
- `PillLayout`
- `PillSurface`
- `TextStyleSpec`

### 7.2 使用原则
- 先找已有组合层，后写页面内临时拼接
- 页面级 pattern 优先建立在 `Vivid` 的轻量 helper 之上
- 如果一个结构跨 2 个以上真实页面稳定复用，就应评估是否上收

### 7.3 当前明确要求
- 顶栏统一使用 `TopBarLayout` 语法
- 路径条统一使用 `PathBarLayout` 语法
- 文本 patch 统一通过 `TextStyleSpec` 生成
- 页面内不再新增“第二套顶栏算法”或“第二套路径条算法”

## 8. 从 PixelPlayer 源码提取出的可执行参考

以下不是“照抄”，而是用于校准我们对目标的感觉：

### 8.1 导航栏
- PixelPlayer 导航栏内容高度定义为 `90.dp`
- 左右内边距存在固定留白：`12.dp / 10.dp` 量级
- 选中态使用 `primary`
- 指示容器偏向 `secondaryContainer`
- 未选中图标/文字偏向 `onSurfaceVariant`

这说明：
- 我们的底栏不能只看图标大小，要把“内容高度、内边距、选中指示容器”一起看

### 8.2 列表项
- `ExpressiveSongListItem` 使用 `56.dp` 封面
- 条目内边距是 `16dp x 8dp` 量级
- 操作图标接近 `24.dp`

这说明：
- 列表项不是靠堆内容显得丰富，而是靠稳定尺寸体系保证信息密度

### 8.3 Library 工具行
- `LibraryActionRow` 默认 fallback 圆角接近 `26.dp`
- 内部图标尺寸约 `20.dp`
- 控件内部常用 `8.dp` 间隔

这说明：
- Shuffle / Sort / Tabs 这些工具件应被看作同一家族

### 8.4 Progress / SeekBar
- PixelPlayer 的 SeekBar 容器使用圆形裁切 + 阴影
- 外层横向 padding 约 `16.dp`
- 内部主要节奏是 `8.dp`
- 波形条 `strokeWidth` 约 `5.dp`
- Thumb 半径约 `8.dp`
- 波长约 `30.dp`

这说明：
- 进度条应被当成“有风格的组件”，而不是一条普通线段

### 8.5 Home 节奏
- `HomeScreen` 中区块间距存在稳定的 `24.dp` 节奏
- Hero 区块高度和统计区块高度都明显大于常规列表行
- Hero 标题存在非常显著的大字号（源码可见 `64.sp` 级别文本）

这说明：
- 首页首先要像“首页”，而不是列表页拼贴版

## 9. 当前阶段的设计验收清单

后续每次做 UI 调整，都优先回答这些问题：

### 9.1 结构验收
- 页面主视觉是否明确
- 信息层级是否能一眼读出来
- 顶栏 / 路径条 / 列表头是否使用统一组合层
- `Library` 列表项是否已具备封面区 / 主信息区 / 辅助信息区 / 尾部区的清晰分工

### 9.2 视觉验收
- 是否仍保持柔和、低对比、厚实的 Expressive 风格
- 颜色有没有因为追求醒目而破坏整体深色基调
- 圆角、阴影、边框是否仍处于同一语言系统内
- 列表项是否仍属于同一视觉家族，而不是一部分像播放器、一部分像系统列表

### 9.3 排版验收
- Hero / Title / Body / Meta 是否层级清楚
- 是否出现“为局部修正而新增裸字号”的情况
- 是否仍遵守显式字体优先级与文本语义映射规则

### 9.4 交互验收
- 可点击区域是否足够大
- 激活、选中、当前播放是否有明确反馈
- 页面切换与状态变化是否会引起不必要布局漂移

## 10. 下一步使用方式

从现在开始，后续推进 `Player UI` 时建议按以下顺序工作：

1. 先在本页新增或修改目标要求
2. 确认该要求属于：视觉 / 结构 / 交互 / 组合层 / 排版 哪一类
3. 再改代码，而不是先改代码再凭感觉讨论
4. 改完后回到本页做对照，判断是否达成要求

如果某一项要求反复推动不动，优先说明：
- 是 `Vivid` 缺能力
- 还是 `Player` 页面级模式还没稳定
- 还是 PixelPlayer 本身用了 Android 平台特性，目前不值得照搬

这样我们讨论的对象会变成“要求本身”，而不是“再大一点、再深一点”。

## 11. 优先级矩阵

为了避免所有问题都显得同样重要，后续要求按优先级处理：

### P0：必须优先满足
- 页面主结构是否正确
- 文本层级是否清楚
- 顶栏 / 路径条 / 列表头是否走统一组合层
- 可点击区域是否足够
- 当前播放 / 选中 / 激活状态是否可识别

### P1：强烈建议尽快满足
- 页面节奏是否接近 PixelPlayer 的“主视觉 + 辅助信息”结构
- 工具区语言是否统一
- 进度条、列表项、卡片等是否具备明确风格身份

### P2：在 P0/P1 稳定后推进
- 更复杂的动效
- 更丰富的装饰细节
- 更精细的渐变、光泽、情绪化视觉层

## 13. 明确禁止项

以下做法后续默认不再接受，除非先更新本规范：

- 在页面里临时新增裸 `FontId / FontWeight / 字号` 来救局部视觉
- 绕过 `TopBarLayout` 再写第二套顶栏矩形推导
- 绕过 `PathBarLayout` 再把路径条当普通 pill 手工拼接
- 为了局部“醒目”直接把颜色推到破坏整体深色基调
- 为了局部“精致”压缩点击面积
- 同一种模式在不同页面上出现两套圆角、间距、图标尺寸规则
- 在 `Library` 列表项问题上，只通过修改 `row_h`、封面大小或文字颜色反复试错，而不先定义目标形态

## 14. 对照表（PixelPlayer -> 当前实现 -> 下一步）

### 16.8 Home 三卡片能力盘点（能力探针）
- `Home` 目前不应只被看成一张首页，它还承担一项职责：作为 `Vivid` 在复杂内容卡片场景下的能力探针页
- 这意味着 `RecommendationCards` 的目标不是“先摆三个静态卡片”，而是逐步验证：卡片是否能稳定承载混合文本、轻交互、状态信息和未来的小型内容部件

#### 当前三张卡片的目标角色
- `Daily MIX`：推荐入口卡，应该承载标题、描述、时长/数量信息，未来可加入小型封面或次级动作
- `Recently Played`：恢复入口卡，应该承载最近内容、恢复语义，未来可加入最近封面、继续播放状态或进度信息
- `Listening stats`：统计卡，应该承载周期头部、总时长、关键指标对、周维度图表；真实 PixelPlayer 版本还会继续延伸到 `Top track` 与专用统计页

#### `Listening stats` 当前阶段的对齐策略
- 参考 `Draft/PixelPlayer/app/src/main/java/com/theveloper/pixelplay/presentation/components/StatsOverviewCard.kt`，真实 PixelPlayer 结构包括：
  - 头部：`Listening stats` + 时间范围 + 右侧前进按钮
  - 主体：总时长大数值
  - 指标行：`Total plays` 与 `Avg per day`
  - 扩展区：`Top track`
  - 底部：一周时间轴柱状图
- 当前 Player 阶段先实现“核心版”，暂不做跳转专用页面，也暂不引入 `Top track`：
  - 头部两行：`Listening stats` / `This Week`
  - 主体一行：总时长大数值
  - 指标一行：`Total plays` / `Avg per day`
  - 底部一行：`Mon` 到 `Sun` 的周维度柱状图
- 右侧箭头可以作为视觉 affordance 保留，但当前不承载真实跳转行为
- 当前核心版的视觉层次也应明确：`Home` 页面底色最深，头部标题带次之，卡片内容面最亮；卡片与柱状图都不依赖描边区分层次
- 周柱状图当前应优先保证“更近、更粗、更高”的观感：柱体较第一版继续加宽约一半、整体高度提高约四分之一，并移除柱体描边/轨道边框感
- 当前数据链路也应明确：这张卡现在不再使用占位值，而是使用真实周统计数据
  - `0 s / 0 / 0 s` 是当前周内尚未发生实际播放时的真实状态，不再是演示文案
  - 当前版本已经支持跨启动持久化本周统计：播放时长与播放次数会按节流策略写回存储
  - 后续如果要进一步对齐 PixelPlayer，再补“多周历史趋势 + Top track + 专用统计页”会更合适

#### 当前已经被验证可用的基础能力
- 卡片表面：`CardBuilder + ListCard surface` 已稳定可用，能承载标题、正文和右侧信息胶囊
- 文本层级：`CardTitle / CardBody / MetaText` 这套语义层已经可用，足以建立卡片内主次关系
- 胶囊信息块：`info_tag / pill_surface / pill_layout` 已可用，适合承载时长、数量、状态等轻信息
- 图片能力：页面内已经能稳定承载封面拼贴，说明卡片未来接入小图/封面不是底层能力问题
- 顶层布局：页面滚动、Hero、卡片区和底部导航已经可以稳定共存

#### 当前能拼出来，但写起来仍偏费劲的能力
- 卡片内左右分区布局：能通过手工 `Rect` 或轻布局拼出，但缺少专门面向内容卡片的内部布局 spec
- 卡片内小型状态组合：例如“标题 + 描述 + meta + 次按钮”，当前能做，但还没有稳定的 pattern helper
- 卡片内图文混排：底层控件都有，但要做出稳定、可复用的内容卡需要较多手工拼接
- 多卡统一节奏：三张卡片虽然能统一表面，但内部内容结构变化一大，就容易重新掉回魔法数阶段

#### 当前最值得暴露出来的能力缺口
- 缺少面向 `Home card family` 的内部组合层，当前只有表面和文字层，没有真正的 `content card spec`
- 缺少小型统计/趋势表达模式，例如：数值对、统计徽标、小型条形/趋势图这类轻量内容部件
- 缺少卡片内轻交互模式，例如：右下角次按钮、恢复动作、局部点击区域的统一组织方式
- 缺少“同一类卡片不同内容密度”的稳定布局策略，当前更适合三张内容结构接近的卡片，不适合差异明显的卡片家族

#### 对当前推进节奏的影响
- `Home` 适合作为能力探针页，优先用于暴露 `Vivid` 是否足以支撑复杂内容卡片
- 但 `Home` 暂时不适合作为第一张高完成度闭环页，因为它太容易提前陷入整体气质微调
- 更合适的推进方式是：先用 `Home` 暴露卡片能力缺口，再回到 `Now Playing` 先做一张完整闭环页，最后再带着补出来的能力回收 `Home`

#### 第一轮 `Listening stats` 原型验证结论
- 旧版原型已验证：`标题 + 趋势胶囊 + 强调数值 + 正文说明 + 目标文案 + 次级按钮 + 紧凑进度条`
- 但它与真实 PixelPlayer 的统计卡结构并不一致，因此本轮将改为对齐“头部 + 总时长 + 双指标 + 周柱状图”的核心版
- 这说明 `Vivid` 现阶段已经不只是在验证静态信息卡，而是在验证：
  - 卡片内部两段式结构
  - 大数字与普通文本共存
  - 双指标并排布局
  - 小型周图表表达
- 这轮也直接暴露出两个值得沉淀的点：
  - `Home` 需要可控滚动截图/验证入口，否则折叠区内容不易稳定回归
  - `ProgressBarSimple` 底层已存在，但先前 `SceneBuilder` 没有暴露创建入口，说明“已有能力未上浮”也是当前的一类真实缺口
- 当前这张卡仍属于能力探针原型，不代表最终视觉定稿；后续如果继续推进，应优先考虑是否抽出 `HomeStatCard / StatCardContentSpec` 一类更稳定的组合层，并补上 `Top track` 这类扩展区块

## 17. Now Playing 页面规格

### 17.1 区块结构
- `TopBar`

- `LyricsPanel`
- `TitleBlock`
- `ProgressSection`
- `MetaInfoRow`
- `PlaybackControls`

### 17.2 区块职责

- `CoverHero`：页面主视觉核心
- `LyricsPanel`：作为 `CoverHero` 的互斥主区状态，承载当前歌词窗口，不改变下方标题、进度和控制区节奏
- `TitleBlock`：承载标题/作者，必须稳定居中
- `ProgressSection`：承载产品级 seekbar 表达，负责播放进度、拖拽预览、提交反馈和不可用降级
- `MetaInfoRow`：承载左右时间与中心状态标签
- `PlaybackControls`：承载上一首 / 播放 / 下一首主交互
- `AuxiliaryPanel`：EQ、音量、Clip 等调试/扩展区域

### 17.3 组件规格
- `TopBar`：左返回 + 标题 + 右操作组
- `CoverHero`：大尺寸单封面，必要时允许辅封面拼贴，但不抢主封面地位
- `TitleBlock`：主标题强于副标题，但不进入 Hero 级别
- `ProgressSection`：当前采用 `progress_visual` 视觉轨道 + `progress` 透明命中区，必须具备稳定 seekbar pattern 身份
- `MetaInfoRow`：必须被看成一个独立信息带，而不是三个散控件
- `PlaybackControls`：主播放按钮必须明显强于侧按钮

### 17.4 状态规格
- 未播放：时间归零、标签区显示初始状态
- 播放中：时间递进、标签反映模式或状态
- 暂停：保留当前信息，不改变整体结构
- Idle：按当前播放时间和已解析 duration 同步轨道、左右时间和中心信息标签
- Dragging preview：轨道 fill/thumb、左侧时间和中心 `Seeking...` 反馈必须立即跟随指针，右侧总时长不变
- Seek committed：提交后至少保留一帧 `Seek queued` 与目标位置反馈，随后回到 idle 同步
- No duration / unavailable：显示稳定空轨与 `0:00 / 0:00`，中心信息清空，不做错误态闪烁
- Lyrics visible：顶部 `Lyrics` 按钮在封面主区和歌词主区之间切换；歌词区显示上一行、当前行、下一行和来源/截断状态，无歌词时显示稳定 fallback

### 17.5 行为规格
- 点击返回：回到主页面，不丢当前播放状态
- 点击/拖拽进度条：命中透明 hitbox，视觉轨道不塌缩；取消拖拽必须恢复到当前播放位置
- 点击控制按钮：立即反映状态变化
- 点击 Lyrics：只切换 Now Playing 主视觉区，不影响播放、seek、封面解析或底部 mini-player
- 点击信息标签：后续可扩展模式切换或提示入口

### 17.6 动效预留
- 封面与标题分层进入
- 进度拖拽反馈可加强
- 信息带状态过渡允许轻淡入，不允许布局变化

### 17.7 当前达成度
- 结构：已达成
- 顶栏：已达成
- 封面主视觉：第一轮视觉恢复已推进，封面舞台回到 PixelPlayer 参考的克制表达：大封面优先，fallback cover 有稳定占位，不主动叠加强阴影、渐变或玻璃效果
- 信息带：第一轮视觉恢复已推进，进度条、左右时间和中心标签现在被更明确地收进同一块播放信息区
- 进度条风格身份：已从“复用 Slider 视觉壳”推进到产品级 seekbar pattern；当前仍不新增专属 widget，后续再评估是否上收到 Vivid
- 控制区主次关系：已达成，第一轮视觉恢复进一步强化了主播放按钮与侧按钮的层级差异

### 17.8 Lyrics 路线
- 当前实现：`player.lyrics` 使用固定容量保存歌词行、时间戳、来源和状态；PlayerController 只保存可见状态、当前行索引和少量显示 scratch，不持有完整歌词文档
- 本地歌词：支持常规 LRC `[mm:ss.xx]` / `[mm:ss.xxx]`、metadata tag 跳过、纯文本 TXT；超出行数、单行容量或 raw 读取上限时显示可用部分并标记 truncated
- 内嵌歌词：FLAC 读取 Vorbis Comment `LYRICS` / `UNSYNCEDLYRICS`；MP3 读取 ID3v2 `USLT`，识别 `SYLT` 但暂记为 unsupported；M4A/MP4 因当前 audio pipeline 尚未接入对应 decoder，作为后续格式支持后的规划项
- 编译期开关：歌词实现暂时保留但默认不进入主线产品/验证路径；`CHARM_PLAYER_LYRICS=OFF` 时 Now Playing 不创建 Lyrics 按钮/面板，H747 evidence 记录 `player_lyrics_profile.enabled=0` 和 `service_size_bytes=0`，后续需要恢复时显式开启该开关
- 非目标：不做网络搜索、数据库、歌词编辑、翻译/罗马音、TTML 或 word-by-word 动画

- 播放 / 暂停：主播放按钮图标立即同步，按钮尺寸和视觉层级不变
- 无媒体库 / 空资源：时间、标签、封面占位和控制区结构保持稳定
- Library 选择后同步：标题、副标题、封面、底部 mini-player 和 Now Playing 主屏同步更新

### 18.7 当前达成度
- 顶栏 / 路径条 / 列表头：已达成
- 工具区统一性：部分达成
- 列表项视觉语言：部分达成（已具备双层文本、当前项状态与播放指示）
- 浏览上下文表达：已达成
- 基础功能闭环：已达成（Tab、Sort、Shuffle、Path 返回、列表进入 context、track 选择、action menu 与 info popup 已纳入 Windows UI CI）

## 19. 组件行为规格

### 19.1 TopBar
- 必须保持轻量
- 必须服务结构，而不是抢正文视觉中心
- 不同页面只允许变体不同，不允许语法不同

### 19.2 PathBar
- 必须表达“当前浏览上下文”
- 默认不是主要操作按钮
- 文本、图标、背景三者必须形成稳定组合

### 19.3 MetaInfoRow
- 必须是一整行独立信息带
- 左右时间与中间标签不能因为文案变化破坏整体平衡
- 未来允许上收为更明确的组合层
- 当前已完成第二轮收敛：时间带已与上方进度条形成更稳定的一体感，中心 `info_tag` 也已具备更明确的状态胶囊身份

### 19.4 SongListItem
- 未来如果继续推进，应优先增强行样式能力
- 若基础 `ListView` 无法满足，应明确建立 expressive 列表行模式

### 19.5 ProgressSection
- 必须优先表达“可拖拽、可感知、可反馈”
- 后续若继续推进，应作为独立风格组件对待
- 当前已完成第一轮收敛：进度条与时间信息带已被收进独立区块，不再只是“一个滑条 + 一排标签”
- 当前已继续推进到第三轮：`idle`、`dragging preview`、`seek committed`、`no duration / unavailable` 四态已形成稳定 contract，并由 Windows `now_playing_seek_*` UI CI 覆盖
- 当前仍保留的真实缺口：交互层仍通过页面内 `Slider + transparent hitbox` 组合承载，尚未形成真正独立的 Vivid `SeekBar` widget

## 21. 实现优先级与依赖

### 21.1 当前优先顺序
- P0：保证结构、层级、可读性、点击性
- P1：强化信息带、列表项、工具区的视觉身份
- P2：在结构稳定后，再做动效和更细情绪化层次

### 21.2 当前最可能的框架依赖点
- `ListView` 行样式能力不足
- `ProgressSection` 已形成页面内产品级 seekbar pattern，并已有轻量 `seek_bar_style` helper；剩余问题是是否值得上收为专属组件
- `MetaInfoRow` 已明显收敛，但仍处于页面内模式，尚未上收

### 21.3 实现策略
- 先写规格，再改代码
- 先在 Player 验证，再决定是否上收回 `Vivid`
- 先收敛组合层，再考虑 builder 或 widget 级抽象
