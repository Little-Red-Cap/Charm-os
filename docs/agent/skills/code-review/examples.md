# Code Review Examples

本文件提供 Charm 项目中代码审查任务的输出范式示例。  
这些示例不是唯一答案，而是帮助 AI 学会：

- 如何组织 review 结论
- 如何区分阻断问题 / 重要问题 / 优化建议
- 如何把问题说清楚，而不是只下判断
- 如何在 Charm 语境下 review，而不是按普通 C++ 项目标准 review

相关文件：
- `SKILL.md`
- `checklist.md`
- `../../rules/charm-architecture.md`

# 示例 1：发现阻断问题的 review

## 输入场景
用户请求：

> 帮我 review 这段串口协议处理代码。

代码中存在以下问题：

- 在协议层 while 循环等待超时
- 使用 `std::vector<uint8_t>` 临时拼包
- 出错时吞掉底层错误并返回布尔值

## 参考输出

### 总体结论
这段实现目前存在阻断问题，不建议合并。

### 阻断问题

#### 1. 协议层出现 busy-spin / 自定义超时等待
当前实现通过 `while (...)` 持续轮询时间并等待数据到达，这违反了 Charm 项目对协议层的约束。  
在本项目中，协议层不应自行做 busy-spin、阻塞等待或自定义超时循环；等待与超时应统一交给 Kernel / EDA 与 `io.reactor` 处理。

**为什么这是问题：**
- 破坏协议层职责边界
- 绕过统一等待模型
- 在 MCU 路径上容易放大实时性与功耗风险

**建议方向：**
将等待逻辑移出协议层，把当前逻辑改写为基于 `would_block` 和统一 reactor 调度的形式。

#### 2. 在该路径中引入 `std::vector<uint8_t>`
当前实现用 `std::vector<uint8_t>` 做临时缓冲，这在 Charm 的 MCU 实时相关路径中不合适。

**为什么这是问题：**
- 引入动态分配风险
- 成本不透明
- 与项目对实时路径容器和内存纪律的要求冲突

**建议方向：**
优先改为固定容量缓冲或 `std::span` + 外部提供的存储。

#### 3. 错误模型退化为布尔值
当前代码在底层失败时只返回 `false`，丢失了原始错误信息。

**为什么这是问题：**
- 吞掉错误码
- 破坏统一错误模型
- 不利于上层判断真实失败阶段

**建议方向：**
改为返回 `util::Result<T>` 或统一错误类型，并向上传递底层 `Errc`。

### 重要问题

#### 4. 包格式语义没有进入类型
当前接口通过多个基础参数表达包语义，阅读者需要依赖注释才能知道哪些字段必须成组出现。

**建议方向：**
可以考虑引入显式的 message/frame 类型，避免把关键协议语义散落在调用参数中。

### 总结建议
这段代码不是简单的小修可过，而是需要先把协议等待模型、缓冲策略和错误模型纠正到项目约束之内，再继续打磨局部实现。

# 示例 2：无阻断问题，但存在重要设计退化

## 输入场景
用户请求：

> 看看这段驱动初始化代码有没有问题。

代码中没有明显违规，但有以下情况：

- 接口使用多个 `int` 和 `bool` 表示模式与选项
- 通过注释解释参数含义
- 使用传统 `.h/.cpp` 拆分，但并非必须

## 参考输出

### 总体结论
未发现阻断问题，可以继续推进，但存在若干重要设计退化，建议在当前迭代中一并修正。

### 重要问题

#### 1. 接口语义过弱，依赖注释理解
当前初始化接口使用多个基础类型参数，例如 `int mode, bool enable_dma, int priority`。  
这类接口虽然能工作，但语义承载能力弱，调用者必须依赖注释和顺序记忆。

**为什么这是问题：**
- 类型系统没有表达关键语义
- 容易出现参数误用
- 与项目强调强类型建模的方向不一致

**建议方向：**
引入 `enum class`、配置结构体或 tag type，把模式和能力声明放到类型层，而不是注释层。

#### 2. 组织方式仍偏传统
当前模块默认按 `.h/.cpp` 方式拆分，但从职责看并没有必须拆分的编译边界或平台隔离需求。

**为什么这是问题：**
- 更像传统物理拆分习惯，而非语义组织
- 不利于项目统一向模块化思维靠拢

**建议方向：**
评估是否可改为更符合 C++ Modules 的组织方式。

### 优化建议

#### 3. 初始化参数可以进一步收紧
部分参数之间存在组合关系，但接口没有体现互斥或依赖关系。  
后续可以进一步把配置约束前移到编译期或构造期。

### 总结建议
方向总体可接受，但这类接口如果现在不收紧，后面会迅速演化成“靠文档和经验使用”的脆弱接口，建议尽早把语义推进到类型层。

# 示例 3：信息不足时的 review

## 输入场景
用户只给了一小段函数：

> 帮我 review 这个 `send_frame()`。

但没有给：
- 所属层级
- 调用路径
- 是否运行在实时路径
- 返回类型上下文

## 参考输出

### 总体结论
基于当前片段，还不能对这段代码是否符合 Charm 项目约束做完整判断，但已经能看到一些值得关注的风险点。

### 当前可见风险

#### 1. 存在潜在的错误模型退化风险
函数内部把多个错误源折叠成统一的失败返回，但从片段中还看不出是否保留了原始 `Errc`。

#### 2. 存在潜在的阻塞风险
当前写法看起来像是同步发送路径，但还无法确认它是否处于协议层或实时路径中。

### 目前无法确认的关键点
要做完整判断，还需要确认：

- 这个函数位于 Foundation / Runtime / IO / Domain 的哪一层？
- 它是否运行在实时路径？
- 它是否通过 `io::Channel` / `io.registry` 工作？
- 返回类型是否是统一的 `util::Result<T>`？
- 上层是否通过统一时间源和等待模型驱动它？

### 暂时建议
在这些上下文明确之前，不建议直接把这段函数判定为“没问题”。  
如果你愿意，我会下一步按 Charm 的 review 维度继续展开，专门检查它的：
- 层次归属
- 错误模型
- 是否阻塞
- 类型语义是否足够
