# Config Module 草案

> status: `exploration`
>
> 本文保留配置模块方向的设计原则，不定义 Charm Core，也不代表当前所有消费方已经完成迁移。
> 具体实现必须以源码、CMake 和实际构建入口为准。

## 目标

- 把构建输入转换为源码可消费的 typed 配置；
- 让稳定公开模块与生成实现模块分离；
- 让兼容别名只负责迁移，不再拥有独立事实源；
- 减少业务代码直接读取散装宏和平铺常量。

## 分层

### 稳定公开表面

公开模块提供长期可依赖的 import 名称和 typed 主表面。它可以做轻量聚合，但不应复制一份
与构建输入或生成模块不同的配置事实。

### 生成实现模块

生成模块把 CMake 的 profile、board、toolchain 和 feature 输入转换为源码可读的值。生成文件
可以随构建系统演进，不应成为业务代码默认依赖的公共名称。

### 兼容层

旧模块名、旧字段名和旧常量名若必须保留，应只转发到新的 typed 表面，并明确标为迁移层。兼容
层不得重新引入硬编码事实，也不得成为新功能的首选入口。

## 构建边界

CMake 仍负责选择目标、工具链、profile 和生成输入；源码负责消费转换后的语义配置。

宏保留在以下边界：

- C、汇编或 vendor SDK 必需的编译定义；
- 控制目标或源文件是否参与编译的开关；
- 编译器、平台和架构探测。

可表达为业务语义的配置，例如产品身份、buffer 上限、队列容量和功能裁剪，不应先设计成
宏或平铺常量，再额外包一层 typed 接口。

## 评审问题

新增配置时至少核对：

1. 它是构建选择、平台事实，还是应用语义？
2. 是否已有稳定 typed 主表面可以承载它？
3. 生成模块和公开模块是否只有一个事实源？
4. 兼容名称是否明确标为迁移层？
5. 源码、CMake、生成文件和验证入口是否同步？

## 当前状态

历史版本曾列出 Player 和 Vivid 的具体样板路径；随着目录迁移，这些路径可能失效，因此不在
本草案中重复维护。需要判断某条配置链是否已落地时，应直接检查对应源码、CMake 接线和构建
产物，而不是引用旧路径或本节文字。

Config Module 仍是可评估的实现组织方式，不是新的 Core 词汇，也不自动授予 `Profile`、
`Board` 或 `Product` 跨平台语义。若未来要提升为稳定契约，应先提交真实消费者、失败语义、
生命周期和跨环境证据，再按 [`CONSTITUTION.md`](../../CONSTITUTION.md) 审查。
