# Charm 方法论总纲：让软件作为系统存在

> [!IMPORTANT]
> **文档状态：`exploration`（冻结扩面）**
> 本文保存方法论背景，不再是 Charm Core 的上位总纲。正式准入与最小契约见
> [`../../../CONSTITUTION.md`](../../../CONSTITUTION.md) 和
> [`../../architecture/charm_core_contract.md`](../../architecture/charm_core_contract.md)。本文中的名词均需重新举证。

## 本文定位

本文不是某个具体机制的设计说明，
也不是 `init.graph`、`Recipe / Plan / Materialize`、`bringup` 的实现手册。

它回答的是一个更高层的问题：

> **Charm 到底想守住什么？**

如果未来出现比当前方案更好的表达方式，
只要它更好地守住本文中的不变量，
它就应该替代今天的实现形式。

---

## 我们真正想解决什么

Charm 真正想对抗的，不是某一种具体写法，
也不是单个模块、单个 HAL、单个平台适配层的工程混乱。

它真正想对抗的是一种更深的宿命：

> 在嵌入式世界里，软件经常不是一个拥有自身秩序的系统，
> 而只是被芯片、SDK、启动文件、链接脚本、HAL、外设接入方式共同挟持出来的产物。

于是每次换平台，软件都像失去自我一样：

- 系统秩序要重写
- 初始化链路要重拼
- 外设接入方式要重适配
- 构建方式要重收口
- 原本属于系统自身的结构，被迫退化成平台偶然性

Charm 要做的，本质上是：

> **把软件自身的秩序，从平台偶然性中解放出来。**

换句话说：

> **换平台，不再意味着重写系统秩序，而是换 profile / binding / board package。**

这不是一句工程口号，
而是 Charm 对嵌入式软件存在方式的根本判断。

---

## 术、法、道

### 1. 术：当前阶段的实现载体

这一层是当前看得见、能落代码、能被替换的机制。

例如：

- `init.graph`
- `Recipe / Plan / Materialize`
- `profile / binding / board package`
- `bringup helper`
- `compat / legacy adapter`

这些都属于“术”。

它们今天很重要，
因为它们正在解决真实的工程问题：

- 初始化混乱
- 能力关系隐式
- 平台迁移重写
- 依赖关系靠人脑记忆
- 系统构成难以验证和观察

但它们不是最终信仰。

---

### 2. 法：更稳定的方法论

这一层比具体写法更稳定，
代表 Charm 已经逐渐形成的方法论。

Charm 当前应长期守住的方法包括：

- 系统秩序必须显式表达
- 依赖关系必须可验证
- 平台差异必须被约束在边界，而不是渗透进整个系统
- 软件构成必须可组合、可裁剪、可迁移、可观察
- 运行时成本必须极低，不能为了“结构优雅”牺牲嵌入式本质

---

### 3. 道：真正不能动摇的方向

这一层才是 Charm 的根命题。

Charm 不是在寻找一种“更好的初始化方式”，
而是在寻找：

> **嵌入式软件如何作为一个系统而存在，而不是作为平台附庸而存在。**

也可以更进一步表达为：

> **Charm 追求的不是更漂亮的工程习惯，
> 而是让嵌入式软件获得主体性。**

这里的“主体性”意味着：

- 它不因平台变化就失去自我
- 它的秩序不是由平台偶然性定义
- 它的结构是显式、可验证、可迁移的
- 它可以被不同平台承载，但不被任何单一平台定义

---

## Charm 的三条根原则

### 原则 1：平台不应定义系统，平台只应承载系统

在传统嵌入式开发中，
平台经常反过来决定系统的长相：

- 用什么芯片
- 用什么 HAL
- 用什么 startup
- 用什么链接方式
- 用什么中断接入习惯
- 用什么供应商 SDK 结构

Charm 要把这个方向倒过来：

> **先有系统，再有平台承载。**

平台是材料，不是系统秩序的来源。

---

### 原则 2：系统秩序必须比平台细节高一级

系统中真正应该稳定的，不是某个 HAL 名字，
不是某个 startup 文件，
也不是某个 vendor SDK 的工程习惯。

真正有价值的东西应该是：

- 因果关系
- 能力关系
- 协作边界
- 生命周期
- 资源归属
- 运行时约束

因此：

> **平台细节应被降级为实现材料，
> 而不是系统秩序的来源。**

---

### 原则 3：好结构不应只被人脑理解，还应能被机器消费

如果系统秩序是显式的，
它就不应只停留在“代码写得比较整齐”。

它还应该能够被：

- 验证
- 可视化
- 生成
- 仿真
- 观测
- 迁移
- 分析资源占用

这也是 Charm 从“架构洁癖”走向“平台潜力”的关键一步。

一旦系统秩序被显式化，
工具链就拥有了统一消费面。

---

## Charm 的稳定不变量

下面这些约束，比任何单一实现机制都更重要。

### 1. 系统秩序必须独立于平台细节存在

一个系统的结构，不应通过：

- 启动文件顺序
- HAL 初始化细节
- 工程目录偶然性
- 入口手工拼装

来被隐式定义。

### 2. 平台变化应被重定义为装配变化

平台切换不应默认等于系统重构。

理想状态下，平台差异应主要体现为：

- profile 变化
- binding 变化
- board package 变化
- capability 装配变化

而不是业务系统秩序被迫重写。

### 3. 系统边界必须显式、可推理、可验证

必须能够回答：

- 什么属于系统自身
- 什么属于平台承载层
- 什么属于领域能力
- 什么属于接入适配层
- 什么关系是依赖，什么关系只是实现材料

### 4. 结构抽象不能以牺牲嵌入式本质为代价

Charm 的结构表达必须始终受以下事实约束：

- MCU / 实时路径资源有限
- 运行时成本必须可控
- 不能为了“语义优雅”引入不可接受的动态开销
- 不能让工具和抽象反过来统治系统

### 5. 系统结构必须可以被机器稳定消费

只要一套秩序不能被机器消费，
它就还没有真正成为平台级结构。

Charm 的结构表达最终应天然支持：

- 静态检查
- 结构导出
- 图形化观察
- 自动生成
- 迁移辅助
- 工具链集成

## 对当前 `init + system bringup` 的定位

`init + system bringup` 之所以重要，
不是因为它的表面语法有多优雅，
也不是因为 `Node` 退幕后这件事本身有多先进。

它真正的价值在于：

> **它第一次比较系统性地把“系统秩序”从平台入口代码与初始化拼装习惯中抽离出来。**

因此，当前阶段我们有理由把它作为主线推进。

但也必须明确：

- 它不是终极答案
- 它不是不能被替代的正统
- 它只是当前最接近这些不变量的一种工程化形式

未来如果出现更高阶、更自然、更易被验证和工具消费的表达方式，
只要它更好地守住本文中的不变量，
就应该允许它替代今天的 `init + bringup` 表面。

---

## 当前阶段复盘：我们已经证明了什么

如果从方法论角度回看这一阶段，
最重要的成果不是“又做出了一套新的初始化写法”，
而是第一次比较完整地证明：

> **系统秩序可以先于具体平台入口而被抽离、归一化、观察、比较，并开始被工具消费。**

这意味着，`init + system bringup` 当前最重要的价值，
不在于：

- `compose(...)` 是否优雅
- `Node` 是否退居幕后
- `Plan` 这组表面是否先进

而在于：

> **它让“系统自身的秩序”第一次有机会脱离平台入口、手工拼装与工程偶然性，作为独立对象存在。**

### 这一阶段已经建立的事实

到目前为止，我们已经初步建立了下面这些事实：

- 系统的协作秩序可以被归一化表达为 capability、依赖边、phase、runlevel、barrier 等关系
- 这些关系可以在 `materialize(...)` 之后稳定落成一份统一结果，而不必等到执行期再去猜测
- 这份结果可以被导出为 `DOT / JSON sample / bundle / diff / report / CI summary`
- 结构差异已经开始能被机器比较，而不只是由人翻入口代码、启动顺序或 board 配置去肉眼判断

换句话说，
我们已经不再只是“在代码里倡导一种结构”，
而是在把这种结构变成可以被验证和审阅的产物。

### 它如何回应最初那几个问题

这一阶段虽然还没有给出终极答案，
但已经对最初那几个问题做出了一个足够清晰的阶段性回答。

#### 1. 什么东西才是系统自身？

当前更接近“系统自身”的，已经不是具体板级入口或某个 HAL 初始化顺序，
而是：

- capability 之间的提供与需求关系
- 节点之间的协作边界
- phase / runlevel / barrier 所表达的生命周期与顺序约束
- `materialized_graph` 中归一化后的系统构成结果

这些东西比平台细节更稳定，
也更接近系统真正的自我描述。

#### 2. 什么东西只是平台偶然性？

当前更接近平台偶然性的，是：

- board package
- binding 方式
- driver / DCD / HAL 的承载细节
- toolchain 与构建目录
- 某个平台习惯使用的入口拼装方式

这些东西仍然重要，
但它们应当更多决定“系统如何被承载”，
而不是决定“系统究竟是什么”。

#### 3. 如何让系统秩序独立于平台而存在？

当前给出的阶段性答案是：

- 先让系统通过统一装配语言进入 `materialize(...)`
- 再让 `materialized_graph` 成为归一化后的观察面
- 在这之后挂导出、diff、报告和 CI，而不是直接从平台入口或执行后端反推结构

这条路径的意义在于，
系统秩序第一次不再依赖某一份 startup 代码、某一份 board 入口或某一个运行时后端才能被理解。

#### 4. 如何让这种秩序既低成本，又可验证，又可被工具理解？

当前这条线之所以成立，
就在于它把观察挂在 `materialize(...)` 之后，而不是挂在执行期副作用之后。

这带来几个直接好处：

- 运行时不需要为了“被观察”而背上额外系统成本
- 工具消费的是归一化结果，而不是零散工程技巧
- 差异可以被脚本、报告和 CI 稳定复用

也就是说，
我们已经初步证明了：

> **系统秩序既可以保持嵌入式可接受的低成本，又可以成为工具后端。**

#### 5. 如何让软件在多平台、多目标机、多构建链之间保持自我同一性？

这一阶段还没有完全解决这个问题，
但已经把问题重定义了一大步：

> **软件是否保持同一性，开始可以被理解为“不同承载条件下，materialized 结果是否仍然表达同一系统秩序”。**

这比过去那种“看入口像不像、看启动顺序像不像、看工程是否改得少”要强得多。

它把“同一性”从工程感觉，
推进成了可以比较的结构问题。

### 这一阶段还没有完成什么

也要实事求是地说，
这一阶段仍然只是开了一个很关键的头，
还远没有抵达终局。

当前仍然存在的边界包括：

- `sample JSON` 还不是最终稳定协议，后面仍需要版本化收敛
- legacy compatibility path 的 capability 名称恢复还没有全部覆盖
- 目前更多是在证明“秩序可见、可比、可被工具消费”，还没有完全证明“跨所有 profile / board / toolchain 都能稳定保持同一性”

所以这阶段真正成立的结论不是：

> `Recipe / Plan / Graph / Bringup` 已经是终极答案。

而是：

> **我们已经找到了一条足够像样的工程路径，能够把“系统秩序”从平台偶然性中提取出来，并把它交给人和工具共同消费。**

这才是它最值得被肯定的地方。

---

## 如何判断一种新机制是前进还是后退

以后评估一条新路线时，
不要优先问：

- 它是不是 `init.graph`
- 它是不是 `Recipe / Plan`
- 它是不是 `bringup`
- 它是不是 capability graph 这套现有表面

而应优先问：

### 1. 它是否让系统更独立于平台？

### 2. 它是否让秩序更显式？

### 3. 它是否让迁移更接近“装配变化”而不是“系统重写”？

### 4. 它是否让验证、可视化、生成、迁移辅助更容易实现？

### 5. 它是否在不牺牲嵌入式约束的前提下做到这些？

如果答案是否定的，
即使它看起来更现代、更优雅，
也不是真正前进。

---

## 对后续架构与工具链的约束

这份总纲对未来工作的直接约束如下。

### 架构设计

- 不把平台细节升级成系统秩序
- 不把暂时的工程技巧冒充为长期结构
- 不让局部方便破坏全局可迁移性
- 不为了表达“高级”而引入不可承受的运行时代价

### bringup / profile / board 演进

- 优先统一系统的自我描述语言
- 优先把系统构成从入口代码中抽离出来
- 优先让 board/profile 只表达承载差异，而不是重写系统秩序

### 工具链建设

- 目标不是为现有写法做一堆脚手架
- 目标是为“显式系统秩序”建立统一消费后端
- 工具设计应服务于验证、观察、生成、迁移，而不是绑定某一代写法

### 迁移策略

- 旧路径可以兼容，但兼容层不应被误当成新主路
- 迁移的终点不是“语法一致”，而是“系统同一性从平台中解放出来”

---

## 一句话总纲

如果只保留一句话，
Charm 的总纲可以压缩为：

> **让嵌入式软件第一次真正作为“系统”存在，
> 而不是作为“平台附庸”存在。**

这句话成立时：

- `Node` 是否存在，不重要
- `Plan` 是否最终保留，不重要
- `bringup` 将来是不是还叫这个名字，不重要
- 甚至 capability graph 的具体表面是否保持不变，也不重要

真正重要的是：

- 平台只是承载层
- 系统秩序独立存在
- 协作边界显式
- 迁移是映射问题，不是重构问题
- 工具可以稳定消费这套秩序

只有做到这些，
Charm 才不只是一个项目路线，
而是在回答一个更根本的问题：

> **软件系统究竟应当以什么方式存在。**
