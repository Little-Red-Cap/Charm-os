# Codegen Workflow

本文件定义 Charm 项目中代码生成类任务的标准执行路径。  
目标是让 AI 在面对接口草拟、模块骨架、实现初稿、适配层草案时，先做正确设计判断，再生成符合 Charm 项目方向的代码。

相关文件：
- `../rules/README.md`
- `../rules/collaboration.md`
- `../rules/embedded-modern-cpp.md`
- `../rules/charm-architecture.md`
- `../skills/codegen/SKILL.md`
- `../templates/codegen-output.md`

---

# 1. 适用范围

本 workflow 适用于以下任务：

- 从零生成某个模块骨架
- 为已有设计生成实现初稿
- 草拟接口
- 生成适配层
- 生成服务层、能力封装层、模块组织草案

不适用于：

- 对现有代码做结论性审查
- 讨论某个系统能力应落在哪一层
- 只做协作方式对齐
- 只做抽象设计比较而不进入代码生成

---

# 2. 总体原则

代码生成任务必须遵守以下原则：

- 先判断需求是否足够明确
- 不明确时先讨论设计，不直接写代码
- 先建模，再写函数
- 先给正确骨架，再补实现细节
- 不为了“完整”而引入违背项目规则的做法
- 代码生成必须显式受 Charm 规则约束

---

# 3. 执行顺序

## 第一步：识别任务类型
先判断当前任务更接近哪一类：

- 新模块骨架
- 接口设计
- 驱动 / 适配层
- 服务层
- 初始化相关节点
- IO / 通道相关实现
- 局部实现补全

若问题本质上是：
- 能力归属未定
- 分层未定
- 装配路径未定

则应先转入架构讨论，而不是直接生成代码。

---

## 第二步：判断需求清晰度
先判断是否已明确以下关键点：

- 该模块属于哪一层
- 能力由谁提供
- 是否走 `init.graph`
- 是否通过 capability / RuntimeContext / registry 注入
- 是否运行在实时路径
- 是否受 IO 非阻塞纪律约束
- 是否已有统一错误模型与时间源前提

若这些关键点不清楚，则应先：

1. 明确指出未确定点
2. 提供 1 到 3 个候选方向
3. 说明取舍
4. 再决定是否进入代码生成

---

## 第三步：加载规则
默认按以下顺序理解规则：

1. `../rules/collaboration.md`
2. `../rules/embedded-modern-cpp.md`
3. `../rules/charm-architecture.md`

说明：

- `collaboration.md` 决定不确定时先讨论设计
- `embedded-modern-cpp.md` 决定类型建模、抽象方向、编译期优先原则
- `charm-architecture.md` 决定 Charm 项目内的具体工程纪律

---

## 第四步：读取技能说明
读取：

- `../skills/codegen/SKILL.md`

目的是明确：
- 生成类任务的目标
- 代码生成流程
- 默认建模偏好
- 输出组织方式

---

## 第五步：先产出设计说明
在真正写代码前，应先给出简要设计说明，至少回答：

- 这个模块/接口在 Charm 中扮演什么角色
- 为什么采用这种建模方式
- 哪些规则影响了当前设计
- 是否还有关键未决点

如果存在多种方案，应先给出：

- 当前推荐方案
- 为什么推荐
- 为什么不优先采用其它方案

---

## 第六步：生成正确骨架
代码生成时应优先保证：

- 分层不被破坏
- 边界清晰
- 接口语义正确
- 能力获取方式一致
- 错误模型一致
- 时间源一致
- IO / 初始化纪律不被破坏

这里的“正确骨架”优先于“实现很满”。

---

## 第七步：补充实现细节
在骨架合理后，再补：

- 具体逻辑
- 错误路径
- 参数约束
- 适配层细节
- TODO

TODO 只能用于明确未决问题，不能掩盖设计不清。

---

## 第八步：套用输出模板
使用：

- `../templates/codegen-output.md`

默认输出结构为：

1. 设计说明
2. 设计取舍（如有）
3. 代码草案
4. 说明
5. 未决点 / TODO
6. 下一步建议

---

# 4. 分流规则

## 应切换到 architect-review 的情况
若代码生成前发现核心问题是：

- 该能力应该放哪一层
- 该能力应放进 `CoreSystemChain` / `BoardChain` / `extra nodes`
- 初始化装配路径未定
- 模块边界存在系统性争议

则应先转入：

- `../skills/architect-review/SKILL.md`

## 应拒绝直接生成的情况
若任务要求的实现明显与 Charm 规则冲突，AI 不应直接照做。  
应先：

- 说明冲突点
- 说明为什么不推荐
- 给出更符合项目方向的替代方案

---

# 5. 代码层默认检查点

在生成代码时，AI 应主动避免：

- 动态分配
- 异常 / RTTI
- 协议层 busy-spin / 阻塞 / 睡眠 / 自定义超时
- 绕过 `init.graph`
- 绕过 `io.registry` / RuntimeContext / capability 注入
- 自建错误模型
- 自建时间源
- 用 `void*` / 裸语义指针承载关键语义
- 用注释替代类型设计
- 用传统物理拆分代替语义组织

---

# 6. 输出风格要求

代码生成输出应保持：

- 先说明，再给代码
- 诚实面对未定点
- 不用“完整但错误”的代码冒充“可落地方案”
- 不用通用模板压平 Charm 的特殊约束

---

# 7. 最终检查

在输出前，AI 应自查：

- 是否先处理了不确定点
- 是否解释了设计意图
- 是否给出了正确骨架而不是错误满配版
- 是否遵守了 Charm 的分层、IO、错误模型、时间源、初始化纪律
- 是否清楚说明了未决点和下一步建议
