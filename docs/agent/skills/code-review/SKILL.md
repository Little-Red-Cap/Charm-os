# code-review

用途：
- 用于 Charm 项目中的代码审查、PR 审查与实现合规性检查。
- 帮助 AI 以一致方式检查实现是否符合 Charm 架构纪律与现代嵌入式 C++ 立场。

适用场景：
- review 某段代码
- review 某个模块设计
- review 某个 PR
- 判断实现是否违反项目规则

不适用场景：
- 从零生成代码
- 纯协作方式讨论
- 仅做抽象技术哲学讨论

依赖规则：
- `../../rules/charm-architecture.md`
- `../../rules/embedded-modern-cpp.md`
- 必要时参考 `../../rules/collaboration.md`
- 涉及事件连接时额外参考 `../../../architecture/signal_state_contract_v0.md`

相关文件：
- `checklist.md`

---

## 1. 目标

本技能的目标不是机械挑错，而是：

- 识别真正重要的问题
- 优先指出违反项目核心约束的点
- 区分“硬性违规 / 强烈不推荐 / 可优化”
- 给出面向修正的建议

---

## 2. 默认理解

进入 review 前默认理解：

- Charm 不是通用 C++ 项目
- 不能用“常见写法”降低标准
- review 首先保护：架构纪律、IO/初始化纪律、错误模型、时间源一致性

---

## 3. 流程

### 3.1 识别对象类型
- 单函数 / 单模块 / 适配层 / PR / 架构级改动

对象越大，审查越关注分层与装配纪律。

### 3.2 先查硬性违规
优先检查：
- 分层反向依赖
- 绕过 `init.graph`
- 协议层 busy-spin / 阻塞等待
- `io::Channel` 返回 `Ok(0)`
- 动态分配 / 异常 / RTTI
- 错误模型不统一
- 时间源不统一
- `signal.emit()` / `post()` / `state` / `connection wiring` 语义错位

### 3.3 再查设计退化
- 类型语义过弱
- 注释替代类型约束
- 传统 `.h/.cpp` 思维回退
- 抽象成本不可解释

### 3.4 最后查优化空间
- 命名可读性
- 模块边界清晰度
- 适配层隔离程度
- 可演进性

---

## 4. 问题分级

- 阻断问题：必须修复，否则不应合并
- 重要问题：建议在当前改动中修复
- 优化建议：可后续迭代

---

## 5. 输出要求

输出应包含：

- 总体结论
- 阻断问题（如有）
- 重要问题（如有）
- 优化建议（如有）
- 不确定点与所需上下文

---

## 6. 风格要求

- 直接、清晰、可执行
- 有依据，不做空泛评价
- 不因“礼貌”弱化结论

---

## 7. 逃生舱处理

看到 escape hatch 类代码时：

- 先检查理由是否明确
- 是否范围最小
- 是否边界隔离
- 是否有标记与文档

若缺失上述条件，至少记为“重要问题”。

---

## 8. 与 rules 的关系

本技能只组织 review 工作方式：

- 架构纪律以 `charm-architecture.md` 为准
- 技术立场以 `embedded-modern-cpp.md` 为准
- 协作方式必要时参考 `collaboration.md`
