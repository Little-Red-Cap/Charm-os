# 示例 1：讨论某个能力应该放在哪一层

## 输入场景
用户请求：

> 我想把日志格式化逻辑直接放到 IO 层里，你怎么看？

## 参考输出

### 当前问题
这不是单纯的实现问题，而是“能力归属”问题。  
核心要判断的是：日志格式化属于 IO 基础能力，还是更高层的输出组织能力。

### 关键判断
我不建议把完整格式化逻辑直接放进 IO 层。

原因有三点：

#### 1. IO 层应优先保持传输/通道职责
IO 层更适合承载：
- 通道
- reactor
- registry
- 非阻塞读写模型

而格式化本身更偏向输出组织和表示层能力。

#### 2. 实时路径和非实时路径对格式化要求不同
如果把格式化直接沉到底层 IO，容易让实时路径也背上不必要的格式化语义和成本。

#### 3. 会模糊边界
“输出”与“IO 传输”虽然相关，但不是同一层问题。  
把它们混在一起，后续会让日志、trace、console、file sink 的职责边界越来越乱。

### 推荐方案
我更推荐：

- IO 层只保留基础通道与写入能力
- 格式化放在更高一层的 out/logging 相关抽象
- 实时路径保留原始字节写入能力
- 格式化仅出现在允许格式化的路径中

### 结论
这个改动不是不能做，而是放错层会让系统边界变差。  
我的建议是：**不要把“格式化”沉到 IO 层，把它保留在输出抽象层。**

# 示例 2：评估某个初始化方案是否合理

## 输入场景
用户请求：

> 现在这个模块我想先在 main 里手写 init 顺序，后面再接回 init.graph，可以吗？

## 参考输出

### 当前问题
这属于初始化装配问题，不是局部实现细节问题。

### 关键判断
我不建议这样做，除非这是一个极短期、强隔离、明确标注的过渡性 bringup 手段。  
在 Charm 里，初始化顺序本身就是架构的一部分，不是可以长期随意漂移的“临时实现细节”。

### 为什么不推荐
#### 1. 会破坏统一装配纪律
一旦允许模块绕出 `init.graph`，后面就很容易出现：
- 入口散落初始化
- 顺序依赖靠经验维持
- bringup 路径和正式路径不一致

#### 2. 会削弱可验证性
当初始化顺序不再统一托管时，系统行为更依赖人工记忆，而不是结构化表达。

#### 3. 临时路径通常会变成长期债务
“后面再接回去”是典型高风险说法。  
如果没有明确时间点、边界和替换计划，这基本上就是在引入长期偏差。

### 推荐方案
更合理的方式是：

- 即使当前只做最小 bringup，也尽量通过 `init.graph` 挂进去
- 如果必须有过渡节点，就把过渡性能力明确隔离
- 给出清晰的替换计划和标记，而不是默认长期保留

### 结论
我的建议是：**不要把 main 手写 init 顺序当常规过渡方案。**  
如果确实必须临时这么做，应把它视为 escape hatch，而不是普通工程选择。

# 示例 3：比较两个设计方案

## 输入场景
用户请求：

> 对于设备发现这块，我有两个方案：
> 1. 运行时注册表里直接存平台对象指针
> 2. 通过强类型 descriptor + capability 组合暴露能力
> 你更推荐哪个？

## 参考输出

### 当前问题
这是典型的“长期演进质量比较”问题，不是只看哪个更省事。

### 我的结论
我更推荐方案 2：**强类型 descriptor + capability 组合**。

### 方案 1 的问题
运行时注册表直接存平台对象指针，短期实现快，但有明显风险：

- 平台细节过早泄露
- 类型语义弱
- 生命周期和所有权关系容易变模糊
- 后面很难保持跨平台一致性

### 方案 2 的优势
强类型 descriptor + capability 组合更符合 Charm 当前方向，因为它：

- 更适合表达能力边界
- 更利于统一装配
- 更容易约束依赖方向
- 更容易做验证与替换
- 更不容易把平台实现细节扩散出去

### 需要注意的点
方案 2 也不是“天然完美”，要注意：

- descriptor 不要退化成纯数据袋
- capability 边界要稳，不能什么都往里塞
- 注册表职责应保持“发现/获取”，不要变成全能容器

### 总结
如果只看短期实现，方案 1 可能更省事；  
但如果按 Charm 的方向看，方案 2 明显更稳，也更值得作为长期方案。
