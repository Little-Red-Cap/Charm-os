# 示例 1：存在阻断问题

## 输入场景
用户请求：

> 请 review 这段串口协议处理代码。

已知问题：
- 协议层 while 循环 busy-spin
- 使用 `std::vector<uint8_t>` 临时拼包
- 出错时吞掉底层错误码

## 参考输出

### 总体结论
存在阻断问题，不建议合并。

### 阻断问题

1) 协议层 busy-spin / 自定义超时循环
- 现象：使用 `while (...)` 轮询等待数据。
- 问题：违反协议层不得 busy-spin 的硬约束，且绕过 `io.reactor`。
- 建议：改为 `would_block + reactor` 驱动模型。

2) 引入动态分配
- 现象：使用 `std::vector<uint8_t>` 拼包。
- 问题：MCU 实时路径禁止动态分配。
- 建议：改为固定容量 buffer 或外部注入 `std::span`。

3) 吞掉错误码
- 现象：底层失败仅返回 `false`。
- 问题：破坏统一错误模型。
- 建议：返回 `util::Result<T>` 并透传 `Errc`。

### 重要问题
- 接口语义依赖注释，建议用强类型表达。

### 总结建议
先修正等待模型、错误模型与内存纪律，再继续细节优化。

# 示例 2：无阻断问题但存在设计退化

## 输入场景
用户请求：

> review 这段驱动初始化代码。

问题：
- 接口参数是多个 `int/bool`
- 语义依赖注释

## 参考输出

### 总体结论
可继续推进，但建议在当前迭代中修复重要设计退化。

### 重要问题
1) 接口语义过弱
- 问题：多个基础类型参数导致语义不清。
- 建议：引入 `enum class` 或配置结构体表达语义。

### 优化建议
- 评估是否可模块化组织，减少 `.h/.cpp` 物理拆分。

# 示例 3：信息不足

## 输入场景
用户请求：

> review 这个 `send_frame()` 函数。

缺失上下文：
- 所属层级
- 是否实时路径
- 返回类型约束

## 参考输出

### 总体结论
信息不足，无法做完整判断，但存在潜在风险点。

### 需要补充的上下文
- 模块层级（Foundation/Runtime/IO/Domain）
- 是否运行在实时路径
- 是否通过 `io::Channel` / `io.registry`
- 返回类型是否统一 `util::Result<T>`

### 暂时风险点
- 可能存在错误模型退化
- 可能存在阻塞等待风险
