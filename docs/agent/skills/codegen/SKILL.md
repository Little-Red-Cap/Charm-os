# codegen

用途：
- 用于 Charm 项目中的代码生成、接口草拟、模块骨架设计与实现建议。
- 帮助 AI 在生成代码时保持与 Charm 项目的协作方式、现代嵌入式 C++ 立场和项目架构纪律一致。

在这些场景使用：
- 从零生成某个模块或接口
- 为现有模块补充实现骨架
- 为某个设计生成初版代码
- 将设计讨论结果落实为符合 Charm 约束的实现方向

不要用于：
- 替代代码评审
- 替代项目级 rules 文件
- 在需求不明确时直接跳过设计讨论
- 对具体 PR 做结论性审查

依赖规则：
- `../../rules/collaboration.md`
- `../../rules/embedded-modern-cpp.md`
- `../../rules/charm-architecture.md`

相关文件：
- `../code-review/checklist.md`

---

# 1. 目标

本技能的目标不是“尽快吐出一段能编译的代码”，而是帮助 AI 生成：

- 符合 Charm 项目立场的实现
- 边界清晰的接口
- 可验证、可演进、低运行时成本的抽象
- 不破坏既有架构纪律的模块骨架

---

# 2. 生成前的默认理解

在进入代码生成任务前，AI 应默认理解：

- Charm 不是普通桌面 C++ 项目
- 不应默认套用“常见 C++ 工程模板”
- 不应为了尽快得到实现而牺牲类型建模与架构纪律
- 需求不明确时，应先讨论方案，再写代码

---

# 3. 代码生成流程

## 3.1 先判断任务清晰度
若任务已经明确到足以生成代码，可进入后续步骤。  
若任务存在关键歧义，则应先：

1. 指出未确定点
2. 给出候选设计方案
3. 说明取舍
4. 再进入代码生成

不应直接跳过设计。

## 3.2 先建模，再落实现
生成代码时应优先确定：

- domain 是什么
- 核心类型是什么
- 边界在哪里
- 能力由谁提供
- 哪些约束应体现在类型里
- 哪些行为必须走 Charm 统一机制

不应先拼函数，再靠注释补语义。

## 3.3 优先生成“正确骨架”
初版代码应优先保证：

- 接口语义正确
- 模块职责清晰
- 不破坏分层
- 不破坏初始化纪律
- 不破坏错误模型与时间源一致性

即使暂未补全全部细节，也应先把骨架方向做对。

## 3.4 再补充实现细节
在骨架合理后，再逐步补：

- 实现细节
- 错误路径
- 参数检查
- 适配层
- TODO 标记

TODO 应表达真实未决问题，而不是掩盖设计缺口。

---

# 4. 生成代码时的默认偏好

## 4.1 类型与接口
默认优先：

- 强类型
- 值语义句柄
- `std::span`
- `std::array`
- `enum class`
- `concept`
- `requires`
- `constexpr`
- `consteval`
- `std::optional`
- `std::expected` 或项目统一结果类型

避免：

- `void*`
- 裸语义指针
- 依赖注释才能安全使用的接口
- 用顺序和约定传递关键语义

## 4.2 模块组织
默认优先：

- C++ Modules
- 接口即实现的清晰组织
- 模块化思维，而不是机械 `.h/.cpp` 拆分

## 4.3 架构纪律
生成代码时必须主动避免：

- 违反 Foundation → Runtime → IO → Domain 分层
- 绕过 `init.graph`
- 绕过 `io.registry`
- 协议层 busy-spin / 阻塞 / 睡眠 / 自定义超时
- 不统一的错误模型
- 不统一的时间源

---

# 5. 输出方式

生成类任务的输出建议分为三段：

## 5.1 设计说明
简要说明：

- 这次代码如何建模
- 为什么采用这种接口形式
- 哪些规则驱动了这个设计

## 5.2 代码草案
提供代码时应：

- 保持清晰结构
- 避免无意义样板
- 不为了“完整”而硬塞错误做法
- 保持 ASCII 风格与 4 空格缩进

## 5.3 风险与未决点
若存在未定部分，应明确说明：

- 哪些部分仍需确认
- 哪些地方先保留 TODO
- 哪些约束尚未验证

---

# 6. 对“能用就行”的处理

若一种实现虽然“能用”，但明显违背项目目标，AI 不应默认采用。  
应优先给出更符合 Charm 项目方向的方案。

必要时可以同时给出：

- 推荐方案
- 保守方案为何不推荐
- 若必须妥协，应如何隔离

---

# 7. 处理外部约束与妥协

若生成任务必须接入第三方 SDK、硬件寄存器或 legacy C 接口，应：

- 将妥协限制在边界处
- 用适配层隔离
- 避免污染核心模块
- 明确标注妥协原因
- 保持核心逻辑仍符合 Charm 的规则

---

# 8. 与其他规则的关系

本技能只定义“如何生成代码”。

- 协作方式以 `collaboration.md` 为准
- 技术方向以 `embedded-modern-cpp.md` 为准
- 项目级架构纪律以 `charm-architecture.md` 为准

本技能不得覆盖这些规则。
