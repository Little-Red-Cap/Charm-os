# DAPLink 脱 Charm 缺口清单

这份清单服务于一个很具体的目标：

把 `Examples/project/daplink` 整理成“可独立构建、可独立理解、可独立公开”的 `STM32 DAPLink` 项目，同时保留一个可选的 `Charm` 集成入口。

## 当前判断

- 适合开源：是
- 更适合公开什么：完整 `STM32 DAPLink` 方案
- 当前最大阻力：不是协议层不完整，而是项目边界和项目口径还没完全收口

## 已经完成的脱钩项

### 1. 默认构建已独立

- 根入口默认不再要求 `Charm-os`
- `DAPLINK_ENABLE_CHARM_INTEGRATION` 变为可选开关，而不是默认前提

### 2. 最小公共能力已本地化

当前这条线已经把先前借住在 `Charm` 名下的最小基础能力收进本目录：

- `base/`
- `io/`

这让 `DAPLink` 不再默认暴露为“私有大仓库里的一个无法单独站立的子目录”。

### 3. 根入口已只认端口目录

当前主入口只认：

- `DAPLINK_PORT_DIR`

这意味着新增 STM32 端口时，不再需要在根入口维护芯片注册名单。

## 仍然存在的缺口

### A. 文档口径还需要继续独立化

虽然现在已经能独立构建，但对外项目首页、构建说明、支持矩阵、限制说明还需要继续打磨。

当前仍建议补齐：

- 一份真正面向外部使用者的项目首页
- 支持端口矩阵
- 已验证工具链 / OpenOCD / Keil 组合说明
- 已知限制与非目标范围

### B. 旧宏兼容仍然存在

当前仍保留 `CHARM_DAP_*` 到 `DAPLINK_*` 的兼容桥，以兼容历史构建入口。
不过这层兼容已经集中收敛到单独入口，而不再散落在多个业务模块里。

这不是功能阻塞，但属于后续可以继续收口的项：

- 保留一段过渡期
- 文档改为只推荐 `DAPLINK_*`
- 等确认外部入口稳定后，再考虑完全去掉旧宏

### C. `io.channel` 的最终归属还没定版

当前是本地最小实现，已经足以满足独立构建。

后续仍有三种可能路线：

1. 继续 vendoring 在本目录
2. 切到你已有的独立开源仓库
3. 折成更小的本地内部抽象

这不是当前阻塞项，但会影响最终对外仓库边界。

### D. 可选 Charm 集成路径还需要单独维护信心

既然保留了 `DAPLINK_ENABLE_CHARM_INTEGRATION=ON`，就意味着它最好：

- 有最小验证路径
- 有明确用途
- 不成为长期失修入口

如果后续使用频率很低，也可以考虑把它降级为“历史兼容入口”，而不是对外主推能力。

### E. 第三方边界与许可证说明还可以更正式

虽然现在已经能从结构上看出：

- 哪些是项目自研
- 哪些来自 STM32Cube / HAL

但如果真的准备独立公开，仍建议补齐：

- 第三方目录来源说明
- 许可证清单
- vendor code 与 project-native code 的边界说明

## 建议顺序

推荐按下面顺序继续推进，而不是同时摊大饼：

1. 先保持独立构建持续可用
2. 再逐步清理旧宏与残余命名
3. 再决定 `io.channel` 是 vendoring 还是外部依赖
4. 最后整理对外仓库首页、许可证与发布口径

## 首发公开范围建议

建议首发保留：

- `app/`
- `frontends/usb/`
- `port/`
- `platform/stm32/`
- 至少一到三个已验证的 STM32 端口

不建议首发承诺：

- 非 STM32 平台支持
- 完全平台无关的 DAPLink 架构
- 所有 IDE / 调试工具的完整兼容矩阵

## 对未来平台扩展的意义

这份清单的价值不只是为了“能不能开源”。

它也在帮我们确认：

- 如果继续加 `STM32` 端口，当前结构已经基本足够
- 如果未来加 `ESP32`，真正会顶到的边界主要在 `platform/` 与 backend，而不是 `app/`

这说明现在最应该做的不是重写协议层，而是继续把平台边界收紧、把项目口径收清楚。
