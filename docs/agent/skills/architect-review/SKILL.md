# architect-review

用途：
- 用于 Charm 项目中的架构评审、设计评估、模块边界判断与演进方向决策。
- 关注结构、边界、装配纪律与长期演进性，而非局部实现细节。

适用场景：
- 判断某个能力是否该存在
- 判断某个能力应该放在哪一层
- 评估改动是否破坏整体架构
- 比较多个方案的长期演进质量
- 评审初始化、能力装配、IO 路径、错误模型等系统性问题

不适用场景：
- 仅 review 小函数的语法或局部实现
- 从零生成完整代码
- 替代项目 rules
- 仅讨论沟通风格而不涉及结构问题

依赖规则：
- `../../rules/collaboration.md`
- `../../rules/embedded-modern-cpp.md`
- `../../rules/charm-architecture.md`
- 涉及事件连接时额外参考 `../../../architecture/signal_state_contract_v0.md`

相关文件：

## 1. 目标

帮助 AI 回答：

- 设计是否符合 Charm 的整体方向
- 能力应放在哪一层
- 抽象是在增强还是污染系统
- 改动是短期便利还是长期退化

重点不是“能否实现”，而是“是否值得这样实现”。

---

## 2. 评审视角

### 2.1 能力视角
- 能力视角优先：所有功能必须以 capability 节点形式注册到 `init.graph`
- 分层只是依赖约束：Foundation / Runtime / Domain 只用于检查依赖方向，不是能力入口
- 验证路径优先：任何新能力都要给最小验证链（host 或 demo）
- 能力边界是否清晰（入口/依赖/装配链）
- 是否绕过 `init.graph` / `io.registry`
- 能力是否具备唯一入口（避免隐式全局）
- 能力是否可替换 / 可裁剪 / 可验证

### 2.2 装配视角
- 是否通过 `init.graph` / `CoreSystemChain` / `BoardChain` / `extra nodes`
- 是否引入隐式初始化或顺序依赖

### 2.3 边界视角
- 是否存在跨层泄漏
- 是否暴露内部细节
- 适配层与核心逻辑边界是否清晰

### 2.4 演进视角
- 是否可持续扩展
- 是否可替换
- 是否可验证
- 成本是否清晰

### 2.5 事件连接视角
- 这是同域同步通知，还是跨上下文投递
- 应该用 `signal.emit()`、`state.set()`，还是显式 `post()`
- 是否把边沿事件和状态真相混成一层
- wiring 是 page/session 临时关系，还是应进入 `init.connection` / materialize 的系统长期拓扑
- 生命周期与 target 所有权是否清楚

## 3. 评审流程

### 3.1 先识别改动类型
- 局部模块设计
- 跨模块能力流转
- 初始化链路调整
- IO 统一入口变化
- 错误模型变化
- 时间源与能力注入变化
- 第三方依赖接入
- 平台边界接入

### 3.2 先看是否破坏硬边界
- 是否破坏能力边界/依赖方向
- 是否绕过统一装配
- 是否绕过统一错误模型
- 是否绕过统一时间源
- 是否在协议层引入等待/轮询
- 是否把平台细节渗透到核心逻辑

### 3.3 再比较方案质量
- 哪个更符合长期方向
- 哪个类型约束更强
- 哪个可验证性更好
- 哪个更少制造技术债

### 3.4 给出落地点建议
- 推荐放在哪一层
- 推荐通过何种能力注入/装配
- 必须保留哪些边界
- 哪些地方允许有限妥协

---

## 4. 输出结构建议

建议按以下结构输出：

1. 当前问题是什么
2. 关键判断依据
3. 推荐方案与原因
4. 不推荐方案与风险
5. 允许妥协的边界（如有）

---

## 5. 默认偏好

- 清晰分层
- 统一装配
- 统一错误模型
- 统一时间源
- 边界隔离
- 编译期建模优先
- 最小必要妥协
- 第三方接口仅停留在边界层

不偏好：

- 跨层调用
- 临时挂载式装配
- “先跑通再重构”的常态化借口
- 平台细节提前渗透到核心抽象

---

## 6. 与 code-review 的关系

- 结构问题优先用本技能
- 局部实现问题再用 `code-review`

---

## 7. 与 rules 的关系

本技能只组织架构评审流程：

- 协作方式以 `collaboration.md` 为准
- 技术立场以 `embedded-modern-cpp.md` 为准
- 项目约束以 `charm-architecture.md` 为准
