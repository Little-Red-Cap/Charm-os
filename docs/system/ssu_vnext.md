# SSU 主线推进纲要 vNext

## 1. 目标定义

以 SSU（可调度语义单元）作为 Charm 的执行语义主轴，
推进系统从“多套执行微体系并存”逐步走向“统一的可声明、可观测、可收敛执行秩序”。

这一阶段的重点不是继续证明 SSU 是否正确，
而是验证它能否稳定扩展、定义边界，并在真实工程中成为默认收敛路径。

## 2. 当前判断

SSU 已经完成了从概念到主线事实层的第一轮跃迁：

- 已有契约文档
- 已有纪律文档
- 已有内核最小骨架
- 已进入 TaskRegistry / scheduler / trace 观测面
- 已接入多个真实 task
- 已在至少一个真实 target 上成为编译事实

因此，SSU 当前不再是“核心抽象候选”，
而应被视为 Charm 的主线执行语义方向之一。

## 3. 下一阶段核心问题

接下来真正需要回答的，不是“SSU 对不对”，而是：

1. SSU 能否稳定吞下更多真实 task
2. SSU 能否定义新的系统边界，而不是只做标签
3. SSU 在扩张时是否会导致复杂度失控

## 4. 阶段目标

### 阶段 A：证明 SSU 不是样板，而是可迁移主线

验收标准：

- 再建立 1 到 2 个干净的严格模式样板 target
- 再覆盖一批高价值 task 的 `ssu_meta()`
- 不新增新的执行旁路
- `tasks/trace/stats` 中的 SSU 标签开始具备真实系统阅读价值

### 阶段 B：让 SSU 从声明层进入提交层

验收标准：

- 明确三类主提交通道：
  - `event-submit`
  - `io-ready-submit`
  - `demand-submit`
- timer/frame 在这一阶段先投影到现有入口，不急于分裂 API
- 新协作模型不得绕过这三类主路径

### 阶段 C：谨慎进入调度行为 SSU 化

验收标准：

- scheduler 至少能基于 SSU 做最弱的一层策略分流
- 不引入复杂 runtime 对象系统
- 不破坏现有已可运行路径
- 能证明收益大于复杂度

## 5. 下一步最值得做的四件事

### 目标 1：建立第二个干净严格模式样板

这是第一优先级。

一个样板说明“可行”；
两个样板才说明“不是巧合”；
三个不同形态样板，才说明“开始具备系统性”。

第二样板应优先满足：

- 依赖少
- 构建链干净
- task 结构清晰
- 能体现与现有样板不同的触发语义

### 目标 2：建立 SSU 迁移优先级表

迁移对象分三层：

#### 第一层：最优先

- pump task
- reactor 驱动 task
- service loop
- 定时推进类 task

#### 第二层：随后纳入

- run loop / phase step
- UI 驱动
- 协议栈推进类 task

#### 第三层：暂缓

- 数据面重、设备时钟主导、IRQ 强耦合路径
- 例如 audio data plane

### 目标 3：把 SSU 标签升级为 SSU 台账

从“能看见 name”推进到“能看见结构”。
后续 observability 应逐步回答：

- 这个 task 属于哪类 trigger
- 它是否 budgeted
- 它是否允许 blocking
- 它 resubmit 频率如何
- 它是否出现预算耗尽
- 它是否长期处于高压热区

### 目标 4：定义 SSU 提交纪律

把以下内容从文档原则升级为开发纪律：

- 新执行模型进入 kernel，必须说明投影到哪类 submit
- 不允许新建临时推进通道绕开 scheduler 语义面
- 如确需绕开，必须声明原因、边界与未来回收路径

## 6. 交付物

本阶段的目标交付物包括：

- 第二个严格模式样板 target
- SSU 迁移优先级清单
- SSU observability 扩展项清单
- SSU submit discipline 草案
- 一份阶段性状态报告更新

## 7. 暂不做

为了避免过早进入“宇宙终极抽象陷阱”，这一阶段明确不做：

- 不重写 scheduler 成完整 SSU runtime
- 不强推所有模块统一 API
- 不急于吞下 audio data plane
- 不引入重型 runtime 多态系统
- 不把所有现有模块都强行迁成同一种编码风格

## 8. 方法模板

推进 SSU 主线时，统一采用如下方法：

1. 先定义一个真实系统目标
2. 再定义该目标的最小闭环
3. 最后从系统阻力点拆出自然子目标

SSU 当前的最小闭环已经很明确：

- task 声明
- registry 识别
- scheduler 可见
- target 严格模式样板
- submit 路径收口

## 9. 当前阶段的一句话口号

先让 SSU 成为 Charm 的默认执行语言，再讨论它是否成为唯一执行机制。

## 10. 当前推进顺序建议

按优先级，接下来只做四件事：

1. 定一份 SSU vNext 推进纲要（本文件）
2. 选第二个干净 target
3. 列第一批必须补 `ssu_meta()` 的 task 清单
4. 写出 submit discipline 草案

在这四步完成前，不急着继续升级 scheduler 的行为统一能力。
