# Charm 复杂场景开发体验改进提案

上位总模型见：`docs/project/charm_工程对象模型草案.md`

本文档用于回答一个已经被 Player/USB/板级 bringup 反复验证的问题：

> 为什么 Charm 在复杂开发需求下“能做”，但“做起来费劲”？

本文不讨论单点功能实现，而讨论：

- 当前复杂场景下的系统性痛点
- 哪些抽象“能用但不好用”
- 在 MCU 约束下，如何提供更高自由度
- 哪些新概念会让开发体验产生质变

目标不是放松架构纪律，而是让复杂开发以更低摩擦进入同一套纪律。

## 1. 结论先行

当前 Charm 的问题不是“没有架构”，而是：

- 系统层抽象方向是对的
- 工程层抽象仍然偏薄

换句话说：

- Core Model 已经开始形成
- Developer Experience Model 还没有完整成型

所以复杂场景下常见体验是：

- 理念上知道应该怎么做
- 真的做起来仍然要手拼很多东西
- 一旦需求复杂，入口、装配、调试和验证成本迅速升高

因此，Charm 下一阶段不应只继续增加能力，而应补上：

> **能力之上的工程抽象层**

## 2. 当前复杂场景的核心痛点

### 2.1 入口与启动链仍然容易分裂

即便系统已经开始朝 `main -> profile -> graph -> run loop` 收敛，复杂项目里仍然很容易出现：

- 主线入口
- bringup 入口
- 实验入口
- debug 入口

这些入口一旦并存，就会让开发者频繁思考：

- 这次应该挂哪条链？
- 哪条链是现在被认可的主线？
- 这次修改会不会又把实验代码带回主线？

这类负担，在复杂项目中会持续消耗注意力。

### 2.2 `init.graph` 正确，但开发粒度偏底层

`init.graph` 是必要的，因为它定义了能力装配纪律。

但在复杂场景中，直接面对 node/capability/requires/provides 的原子粒度，开发体验偏“内核层”，不够“工程层”。

表现为：

- 装配代码样板偏多
- 场景切换成本偏高
- 能力组合要手工拼接
- 一旦场景变多，结构容易发散

所以它是“能用”的，但还不够“顺手”。

### 2.3 板级事实与场景策略容易缠在一起

复杂 MCU 项目里会同时出现这些信息：

- HAL 句柄
- 中断与 DMA 约束
- memory region 限制
- 外设初始化顺序
- 某个实验场景启哪些能力
- 某个 profile 是否开启某条路径

如果缺少清晰的中间层，代码很容易变成：

- board 和 profile 混写
- runtime 和业务混写
- bringup 和实验目标混写

这会导致架构纪律正确，但工程结构不断脏化。

### 2.4 实验代码缺少“制度化容器”

复杂开发一定需要实验。

问题不在于“有实验代码”，而在于：

- 实验是否有长期职责位置
- 实验是否能作为正式场景存在
- 实验是否会污染主线结构

如果没有受控机制，实验代码就会变成：

- 临时入口
- 特殊主函数
- 条件编译岔路
- 看起来像测试目录、实际上承载主线逻辑的目录

这类结构非常伤长期演进能力。

### 2.5 可观测性不是系统一等公民

复杂场景下，最贵的不是写代码，而是定位问题。

尤其在 MCU 环境下，常见问题包括：

- 枚举阶段失败
- DMA/中断时序问题
- 存储初始化抖动
- 多子系统并发时的状态紊乱
- 内存区域使用不符合外设限制

当前日志/trace/counter 能用，但整体更像“按需补丁”，还不像“系统默认能力”。

这会直接拉高复杂项目调试成本。

### 2.6 资源约束还没有完全升格为架构概念

对于单片机项目，下面这些不是实现细节，而是第一性约束：

- 哪块内存可 DMA
- 哪块内存适合实时状态
- 哪块内存适合大缓冲
- 哪类任务允许阻塞
- 哪类路径必须固定预算

如果这些约束只是散落在经验、注释和板级实现里，那么系统虽然能跑，但无法形成高层可组合抽象。

### 2.7 分层规则存在，但“顺手工具”不足

Charm 已经有明确分层与依赖红线。

但复杂项目开发时，工程体验仍然常常是：

- 知道不能这样依赖
- 但一时找不到更顺手的落点
- 最后靠人工克制，而不是靠结构自然引导

说明目前规则比结构更强，约束比工作流更完整。

系统要真正顺手，应该让“正确路径”比“错误路径”更自然。

## 3. 哪些是“能用但不好用”的

### 3.1 `init.graph`

- 优点：统一能力装配、显式依赖、适合系统纪律
- 问题：直接暴露给复杂场景开发时粒度太低

结论：

- 它应该继续保留为底层核心机制
- 但不应继续承担全部工程层表达责任

### 3.2 Capability 模型

- 优点：非常适合 Charm 的世界观
- 问题：单 capability 的表达很强，但多 capability 的“成组场景表达”还不够成熟

结论：

- capability 是对的
- 但需要更高一层的组合抽象

### 3.3 C++ Modules

- 优点：边界清晰、依赖显式、适合长期架构收敛
- 问题：构建链、迁移成本、报错体验仍然偏脆

结论：

- 可以用，而且值得坚持
- 但需要更稳定的工程组织方式来降低心智负担

### 3.4 统一 `out` / 非异常 / 零分配约束

- 优点：对 MCU 是正确方向
- 问题：当工程抽象层不足时，这些约束容易让开发者感受到“限制”，而不是“赋能”

结论：

- 这些原则不应放松
- 但必须配套更好的开发便利层

### 3.5 示例工程驱动演进

- 优点：可以用真实压力验证架构
- 问题：如果缺少 runtime/profile 结构，就容易变成实验代码堆积区

结论：

- 示例驱动是对的
- 但必须制度化“实验如何进入主线”

## 4. 在 MCU 约束下，如何给更高自由度

复杂项目里真正需要的自由，不是“随便写”，而是：

> **在不破坏系统纪律的前提下，更低成本地表达复杂场景**

因此，Charm 需要的不是放松约束，而是：

- 保留低层纪律
- 提升高层表达力

一句话概括：

> **把自由度放在“场景声明”上，而不是放在“随便接线”上**

## 5. 哪些概念会带来质变

### 5.1 `Profile / Scenario`

这是最关键的概念。

开发者不该再通过：

- 改 `main`
- 注释 CMake 源文件
- 复制一份实验入口

来表达场景差异。

开发者应该声明：

- `usb_self_msc`
- `usb_storage`
- `usb_audio`
- `player_core`
- `player_ui_ink`

然后系统用统一启动主线加载它。

这会把“改入口”升级为“选场景”。

### 5.2 `Runtime`

`runtime` 应该成为正式概念，而不是临时目录名。

它负责表达：

- 板级 bringup 后的宿主事实
- HAL/中断/DMA/clock/PCD/UART/SDMMC 等运行时绑定
- 为 profile 提供能力挂接点

`runtime` 不是业务，也不是测试。

它是：

> **场景运行所依赖的板级宿主环境**

### 5.3 `Capability Bundle`

当前 capability 太原子化。

复杂场景中，开发者常常需要的是：

- 一组一起出现的能力
- 一组一起注册的节点
- 一组一起启用的 contract

因此应引入 bundle 概念，例如：

- `usb_storage_bundle`
- `player_storage_bundle`
- `audio_output_bundle`
- `ui_ink_bundle`

底层仍然是 graph/node/capability，
但工程层不再每次从原子粒度手拼。

### 5.4 `Resource Class / Memory Class`

这是 MCU 复杂项目极重要、但目前仍不够显式的概念。

建议将资源约束抽象成正式分类，例如：

- `dma_safe`
- `fast_tcm`
- `framebuffer_sdram`
- `large_stream_buffer`
- `persistent_backup`

然后让 buffer、driver、runtime、profile 显式声明资源需求。

这样就能把“板级经验”升格为“架构可组合信息”。

### 5.5 `Bringup Recipe`

不是所有项目都应该自己重写 bringup 顺序。

Charm 应提供正式 recipe 概念，例如：

- `minimal_board_recipe`
- `storage_recipe`
- `usb_device_recipe`
- `player_core_recipe`

recipe 的职责是：

- 定义 bringup 次序
- 装配共性能力
- 统一常见初始化路径

这样 profile 只负责声明差异，而不是重复拼基础顺序。

### 5.6 `Observability Contract`

复杂场景调试必须系统化。

建议把以下能力变成可选但标准化的 contract：

- counter
- trace point
- phase log
- state snapshot
- last error record
- timing histogram

这样每个复杂子系统都能在同一套语言里被观测，而不是临时打印。

### 5.7 `Host Parity`

复杂项目不应该过度依赖“烧录到板子上才知道对不对”。

应强化 host parity：

- 同一 profile 在 host 上是否能跑 stub
- 同一 bundle 在 host 上是否能过逻辑验证
- 同一 observability contract 是否能在 host 上输出同样结构的调试信息

这对 MCU 开发体验提升会非常明显。

## 6. 推荐的三层工程抽象

对于复杂项目，建议正式形成三层表达：

### 第一层：`runtime`

回答的问题：

> 板级宿主环境是什么？

负责：

- HAL 绑定
- 句柄
- 时钟
- 中断
- DMA
- memory region
- driver adapter

### 第二层：`bundle`

回答的问题：

> 哪些能力需要一起出现？

负责：

- 一组能力的统一接入
- 一组 node 的组合
- 一组 contract 的封装

### 第三层：`profile`

回答的问题：

> 这次我要跑什么场景？

负责：

- 选 bundle
- 决定启哪些 capability
- 决定 run mode
- 决定验证或业务目标

这三层组合后，复杂项目会从“接线式开发”变成“声明式开发”。

## 7. 哪些改进最优先

### P0：把 `Profile / Runtime` 定为正式概念

这是已经在 Player 中开始验证的方向，应继续强化。

目标：

- 新场景不再新增 `main-xxx.cpp`
- 新场景都通过 profile 接入
- runtime 成为板级宿主层标准命名

### P1：引入 `Capability Bundle`

目标：

- 降低 graph 直连成本
- 提升复杂场景装配表达力

### P2：引入 `Resource Class`

目标：

- 把单片机资源约束显式建模
- 减少“经验依赖”

### P3：引入 `Observability Contract`

目标：

- 让复杂调试不再依赖临时日志补丁

### P4：统一 Host/Stub 验证策略

目标：

- 降低 MCU 侧迭代成本
- 把复杂逻辑更早放到 host 验证

## 8. 对 Charm 当前阶段的判断

Charm 现在最不缺的是再做一个新子系统。

最缺的是：

> **让复杂项目以更低摩擦进入现有系统纪律**

这意味着下一阶段的重点不应只是“能力扩张”，而应是：

- 工程抽象升级
- 场景表达升级
- 调试与验证体验升级

如果这一步做成，Charm 会从：

- 一个拥有正确系统观的架构

进一步变成：

- 一个在复杂 MCU 项目里真正顺手的开发平台

## 9. 当前可执行建议

结合当前仓库现状，建议按以下顺序推进：

1. 固化 `profile / runtime` 语义与目录职责
2. 把新功能接入限制在 `profile` 主线
3. 设计第一批 `bundle`
4. 为 USB / Storage / Audio 设计统一 observability contract
5. 把 memory / DMA 约束升格为 resource class

其中第 1 步和第 2 步，Player 已经开始落地；
后续应把这套经验反向抽象回 Charm 系统层。
