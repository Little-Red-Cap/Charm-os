# code-review

用途：
- 用于 Charm 项目中的代码审查、PR 审查、设计实现合规性检查。
- 帮助 AI 在 review 场景下以一致方式检查实现是否符合 Charm 项目的架构纪律、现代嵌入式 C++ 立场和协作预期。

在这些场景使用：
- review 某段代码
- review 某个模块设计
- review 某个 PR
- 判断实现是否符合 Charm 项目规则
- 判断实现是否在关键点上退化到不符合项目目标的写法

不要用于：
- 从零生成代码
- 单纯讨论协作方式
- 只做抽象技术哲学讨论而不针对具体实现
- 替代项目级 rules 文件本身

依赖规则：
- `../../rules/charm-architecture.md`
- `../../rules/embedded-modern-cpp.md`
- 必要时参考 `../../rules/collaboration.md`

相关文件：
- `checklist.md`

---

# 1. 目标

本技能的目标不是机械挑错，而是帮助 AI 在 Charm 项目中完成高质量 review：

- 先识别真正重要的问题
- 优先指出违反项目核心约束的问题
- 区分“硬性违规”“强烈不推荐”“可讨论优化”
- 给出面向修正的意见，而不是泛泛而谈

---

# 2. review 前的默认理解

在进入 review 前，AI 应默认理解：

- Charm 项目不是普通通用 C++ 项目
- 不应按“常见工程习惯”做宽松评价
- 不应因为某写法“常见”“容易理解”就忽略其与项目立场的冲突
- review 应优先保护项目的：
    - 架构纪律
    - IO 与初始化纪律
    - 错误模型一致性
    - 时间源一致性
    - 现代嵌入式 C++ 设计方向

---

# 3. review 流程

## 3.1 先识别任务对象
先判断 review 的对象属于哪一类：

- 单个函数
- 单个模块
- 某个适配层
- 某个 PR / 多文件变更
- 架构级改动

不同对象的 review 深度不同，但检查维度应一致。

## 3.2 先查硬性问题
优先检查是否存在以下问题：

- 违反模块分层
- 绕过 `init.graph`
- 违反 IO 非阻塞纪律
- 引入动态分配
- 引入异常 / RTTI
- 协议层 busy-spin / 阻塞 / 睡眠 / 自定义超时循环
- 吞错误码
- 自建不统一错误模型
- 自建时间源
- 绕过 `io.registry` / RuntimeContext / 统一能力注入
- 直接污染核心逻辑的脏接口

这类问题优先级最高，应先指出。

## 3.3 再查设计退化
若没有明显硬性违规，再检查是否存在设计退化，例如：

- 用运行期分支代替编译期建模
- 用注释承载本应由类型表达的语义
- 使用 `void*`、裸指针、隐式顺序约定
- 以传统 `.h/.cpp` 思维替代模块化组织
- 设计明显回退到“能用就行”的低标准方案

## 3.4 最后查改进空间
在硬性违规和设计退化之外，再讨论：

- 命名是否清晰
- 接口是否还可以进一步收紧
- 抽象成本是否清晰
- 妥协点是否隔离充分
- 是否存在更符合项目目标的替代方案

---

# 4. 问题分级

review 时应将问题分为三类：

## 4.1 阻断问题
必须修改，否则不应通过：

- 违反项目硬性规则
- 破坏架构边界
- 破坏运行时/实时路径纪律
- 破坏统一错误模型、统一时间源、统一初始化纪律

## 4.2 重要问题
建议在当前改动中修复：

- 明显设计退化
- 引入强烈不推荐项却无理由说明
- 边界隔离不充分
- 可维护性明显下降

## 4.3 优化建议
可后续迭代处理：

- 更强类型化
- 更清晰的命名
- 更优的模块边界
- 更一致的表达方式

---

# 5. 输出方式

默认输出应尽量包含以下部分：

## 5.1 总体结论
一句话说明这次 review 的总体判断，例如：

- “存在阻断问题，不建议合并”
- “总体方向正确，但有若干重要问题需要修正”
- “未发现阻断问题，可继续推进，但有若干优化建议”

## 5.2 主要问题
按优先级列出问题：

- 阻断问题
- 重要问题
- 优化建议

每条问题应尽量包括：

- 现象
- 为什么是问题
- 违反了哪类规则
- 推荐修正方向

## 5.3 若信息不足
若无法确认某点，应明确写出：

- 当前无法判断什么
- 还需要哪些上下文
- 暂时的风险判断是什么

不应装作已经确认。

---

# 6. review 语言风格

默认采用：

- 直接
- 清晰
- 高标准
- 不委婉粉饰问题
- 但仍保持建设性

应避免：

- 情绪化批评
- 空泛评价
- “看起来还行”
- 没有依据的主观断言

---

# 7. 处理妥协代码

若看到 escape hatch 类代码，不应直接判死刑。应先检查：

- 是否有明确理由
- 是否范围最小化
- 是否边界隔离充分
- 是否有注释与文档
- 是否有后续复审计划

若妥协代码没有这些保障，则应作为重要问题或阻断问题指出。

---

# 8. 与 rules 的关系

本技能只定义 review 工作方式。

- 项目约束判断以 `charm-architecture.md` 为准
- 技术方向判断以 `embedded-modern-cpp.md` 为准
- 协作方式判断在必要时参考 `collaboration.md`

本技能不得替代这些规则文件。
