# Code Review Checklist

本清单用于 Charm 项目中的代码审查。  
使用时应优先结合以下规则文件：

- `../../rules/charm-architecture.md`
- `../../rules/embedded-modern-cpp.md`

本清单不是规则来源，而是 review 时的检查辅助。

---

# 1. 阻断项检查

## 1.1 运行时与内存
- [ ] 是否引入了动态分配？
- [ ] 是否在 Kernel / 驱动 / 实时回调路径中使用了不允许的动态容器？
- [ ] 是否引入了异常或 RTTI？

## 1.2 初始化与装配
- [ ] 是否绕过了 `init.graph`？
- [ ] 是否把底座能力错误放入 `extra nodes`？
- [ ] 是否引入了散落的临时 Caps 结构？

## 1.3 IO 与协议纪律
- [ ] `io::Channel::read/write` 是否保持非阻塞？
- [ ] 是否存在 `Ok(0)` 返回？
- [ ] 资源暂不可用时，是否正确返回 `Errc::would_block`？
- [ ] 协议层是否出现 busy-spin、阻塞等待、睡眠等待或自定义超时循环？
- [ ] 是否绕过 `io.reactor` / Kernel / EDA？
- [ ] 是否绕过 `io.registry` 或统一注入路径？
- [ ] 是否在业务层直接轮询硬件，而不是通过 `input.service`？

## 1.4 错误模型
- [ ] 是否正确使用 `util::Errc`？
- [ ] 是否正确使用 `util::Result<T>`？
- [ ] 是否吞掉错误码？
- [ ] 是否新建了不统一的 Error 结构体？

## 1.5 时间源
- [ ] 是否绕过 `charm.system.clock`？
- [ ] 是否自建 `now_ms` / `now_us`？
- [ ] 是否未通过统一 Clock 注入获取时间？

## 1.6 模块分层
- [ ] 是否违反 Foundation → Runtime → IO → Domain 的依赖方向？
- [ ] 是否存在反向渗透？
- [ ] 是否暴露了不该暴露的内部细节？

---

# 2. 重要问题检查

## 2.1 设计建模
- [ ] 是否用运行期分支模拟编译期选择？
- [ ] 是否把语义写进注释，而不是类型？
- [ ] 是否使用了 `void*` 且没有充分理由？
- [ ] 是否使用裸语义指针作为接口参数？
- [ ] 是否通过顺序或约定隐式传递语义？

## 2.2 抽象与接口
- [ ] 接口是否足够强类型？
- [ ] 是否优先使用值语义句柄、`std::span`、`std::array` 等更符合项目方向的形式？
- [ ] 抽象成本是否可解释？
- [ ] 是否为了“更熟悉”而主动退回传统写法？

## 2.3 模块组织
- [ ] 是否不必要地回退到 `.h/.cpp` 拆分？
- [ ] 是否让物理文件拆分替代了语义分层？
- [ ] 是否存在边界不清的模块职责？

## 2.4 输出与日志
- [ ] 是否使用了 `printf/snprintf` 而不是 `out::format / out::printf`？
- [ ] 是否在实时路径中做了格式化或分配？
- [ ] 是否错误使用了日志路径？

## 2.5 第三方与构建
- [ ] 是否引入了不受控第三方依赖？
- [ ] 是否在核心路径中引入了必须联网的依赖？
- [ ] 第三方库是否缺少开关控制？
- [ ] 是否遗漏了 PC / MCU 双端构建验证要求？

---

# 3. 逃生舱口检查

- [ ] 妥协是否有明确理由？
- [ ] 妥协是否只发生在边界处？
- [ ] 妥协范围是否已最小化？
- [ ] 是否有 `ESCAPE_HATCH` 类标记？
- [ ] 是否有 benchmark、设计文档或外部约束说明？
- [ ] 是否有后续复审或移除计划？

---

# 4. 优化项检查

- [ ] 命名是否清晰、语义是否稳定？
- [ ] 是否可以进一步缩小接口表面？
- [ ] 是否可以进一步加强类型约束？
- [ ] 是否可以进一步减少运行期成本暴露不清的问题？
- [ ] 是否可以更好地隔离适配层与核心逻辑？

---

# 5. review 输出建议

输出时建议按以下顺序组织：

1. 总体判断
2. 阻断问题
3. 重要问题
4. 优化建议
5. 未确认但值得关注的风险点

若未发现阻断问题，也不应自动等于“设计优秀”；仍应检查是否存在明显退化或可改进项。
