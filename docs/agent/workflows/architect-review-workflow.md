# Architect Review Workflow

本文件定义 Charm 项目中架构评审类任务的标准执行路径。  
目标是让 AI 在面对模块边界、能力归属、初始化装配、系统演进方向等问题时，先做结构判断，再给出建议，而不是直接落入局部实现细节。

相关文件：
- `../rules/README.md`
- `../rules/collaboration.md`
- `../rules/embedded-modern-cpp.md`
- `../rules/charm-architecture.md`
- `../skills/architect-review/SKILL.md`
- `../templates/architect-review-output.md`
- `../glossary.md`

---

# 1. 适用范围

本 workflow 适用于以下任务：

- 讨论某个能力应该放在哪一层
- 评估某个模块设计是否合理
- 判断某个改动是否破坏系统边界
- 比较多个架构方案
- 讨论初始化装配、能力注入、IO 路径、错误模型、时间源等系统性问题
- 讨论第三方 SDK / 平台能力应如何隔离

不适用于：

- 单纯 review 某个小函数是否违规
- 从零直接生成完整代码
- 纯粹的协作方式对齐
- 不涉及系统结构的局部语法或实现问题

---

# 2. 总体原则

架构评审必须遵守以下原则：

- 先判断当前问题属于哪类结构问题
- 先看分层、边界、装配，再看局部实现
- 先判断长期演进质量，再判断短期实现便利性
- 不把“先跑起来再说”当成默认架构策略
- 不把局部方便凌驾于系统一致性之上
- 允许有限妥协，但必须边界清晰、范围最小、理由明确

---

# 3. 执行顺序

## 第一步：识别问题类型
先判断当前问题的核心属于哪一类：

- 能力归属问题
- 模块边界问题
- 分层依赖问题
- 初始化装配问题
- IO 路径与等待模型问题
- 错误模型一致性问题
- 时间源一致性问题
- 平台边界 / 第三方适配问题
- 系统长期演进方向问题

若问题本质上只是“某段实现是否违规”，应切回 `code-review`，而不是用架构评审 workflow 处理。

---

## 第二步：加载规则
默认按以下顺序理解规则：

1. `../rules/charm-architecture.md`
2. `../rules/embedded-modern-cpp.md`

若问题还涉及：
- 多种方案未定
- 需要先对齐讨论节奏
- 需要先说清取舍再下结论

则再补充：

3. `../rules/collaboration.md`

说明：
- `charm-architecture.md` 用于项目级结构与装配判断
- `embedded-modern-cpp.md` 用于技术方向、抽象质量与长期立场判断
- `collaboration.md` 用于处理不确定性与方案讨论方式

---

## 第三步：统一术语理解
若问题涉及项目内关键术语，应优先参照：

- `../glossary.md`

重点确认术语含义，包括但不限于：

- `init.graph`
- `CoreSystemChain`
- `BoardChain`
- `extra nodes`
- `io::Channel`
- `io.reactor`
- `io.registry`
- RuntimeContext
- `util::Errc`
- `util::Result<T>`
- `charm.system.clock`
- capability
- escape hatch

若术语在当前上下文中仍不够明确，应明确说明，不要自行发明含义。

---

## 第四步：读取技能说明
读取：

- `../skills/architect-review/SKILL.md`

目的是明确：
- 架构评审关注什么
- 默认使用什么视角
- 如何比较多个方案
- 如何输出推荐与不推荐方案

---

## 第五步：先判断是否存在硬边界问题
优先检查是否存在以下问题：

- 违反 Foundation → Runtime → IO → Domain 分层
- 本应统一装配的能力被散落在入口或局部逻辑中
- 绕过 `init.graph`
- 本应走 capability / RuntimeContext / registry 的能力被内部偷取
- IO / 协议等待模型被错误地下沉到不该承担的层
- 统一错误模型被破坏
- 统一时间源被破坏
- 第三方或平台细节污染核心逻辑
- `extra nodes` 被当成兜底杂物区使用

这类问题优先级最高，应先明确指出。

---

## 第六步：再判断方案质量
若没有明显硬边界违规，或多个方案都“能做”，则继续比较：

### 6.1 分层质量
- 哪个方案边界更稳？
- 哪个方案更少跨层渗透？
- 哪个方案更少暴露内部细节？

### 6.2 装配质量
- 哪个方案更符合统一装配路径？
- 哪个方案更利于能力注入？
- 哪个方案更少依赖临时初始化顺序？

### 6.3 抽象质量
- 哪个方案更强类型？
- 哪个方案更利于验证？
- 哪个方案更少把语义藏进约定或注释？

### 6.4 演进质量
- 哪个方案更容易扩展？
- 哪个方案更容易替换？
- 哪个方案更少制造后续债务？

---

## 第七步：判断是否需要有限妥协
若当前问题确实受制于：

- 硬件强制约束
- 第三方 SDK / C 接口限制
- benchmark 支撑的性能关键路径

则可以讨论 escape hatch，但必须同时判断：

- 妥协范围是否最小化
- 是否隔离在边界处
- 是否有清晰标记
- 是否有说明文档
- 是否不会污染系统核心

若这些条件不满足，则不应把妥协当成合理方案。

---

## 第八步：套用输出模板
使用：

- `../templates/architect-review-output.md`

默认输出结构为：

1. 当前问题
2. 我的结论
3. 关键判断
4. 推荐方案
5. 不推荐方案
6. 下一步建议

---

# 4. 分流规则

## 应切换到 code-review 的情况
若当前问题本质上是：

- 某段实现是否引入动态分配
- 某个函数是否吞错误码
- 某段代码是否违反非阻塞纪律
- 某个 PR 是否存在阻断问题

则应切换到：

- `../skills/code-review/SKILL.md`

## 应切换到 codegen 的情况
若当前讨论已基本完成，下一步需求变成：

- 按某个推荐架构生成代码骨架
- 生成模块接口
- 生成适配层初稿

则应切换到：

- `../skills/codegen/SKILL.md`

## 应补充 collaboration 的情况
若当前属于多方案讨论，且方案取舍高度依赖人的偏好，应补充使用：

- `../rules/collaboration.md`

并先对齐设计取舍，而不是直接宣布唯一答案。

---

# 5. 输出风格要求

架构评审输出应保持：

- 先给结论
- 再给依据
- 再给推荐落点
- 允许直接指出不推荐方案
- 不绕弯，不空泛，不只讲抽象大词

避免：

- 只说“我觉得不太优雅”
- 只讲理念，不给落点
- 只说不行，不说应该怎么放
- 把局部方便误当作架构合理性

---

# 6. 最终检查

在输出前，AI 应自查：

- 是否先识别了问题类型
- 是否优先检查了硬边界问题
- 是否比较了长期演进质量，而不只是短期实现便利
- 是否明确给出了推荐方案和理由
- 是否在需要时诚实说明术语或上下文仍不够明确
- 是否把架构问题错误降级成了局部实现问题
