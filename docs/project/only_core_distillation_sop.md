# OnlyCore 提纯 SOP

## 文档状态

- `status`: `supporting`
- `scope`: OnlyCore 分支的提纯流程、证据和归档
- `authority`: [`../../CONSTITUTION.md`](../../CONSTITUTION.md)

## 1. 目的

OnlyCore 是一次有期限的提纯工作区，不是长期产品线，也不承诺合并回旧 Charm 主线。

旧主线在提纯期间保持冻结。提纯完成后，主线只选择性借鉴经过验证的契约、代码、测试和构建结果。

## 2. 启动基线

开始前必须完成：

1. 获取远端引用，确认本地/远端 `OnlyCore` 是否已存在及其共同祖先。
2. 若远端已存在 `OnlyCore`，让本地分支跟踪它；不得另建同名历史或用强推覆盖。
3. 将提纯范围外的未提交内容保存到独立快照分支；不丢弃已有改动。
4. 显式暂存 Core 契约、最小实现、测试和证据入口，建立语义基线提交。
5. 创建不可移动标签 `onlycore-baseline`；标签说明不得宣称 Core 已独立构建。
6. 回到跟踪远端的 `OnlyCore`，确认工作区干净后再删除外围内容。

禁止在未检查 `origin/OnlyCore` 前直接执行 `git switch -c OnlyCore`。本地与远端分叉时先保留双方
提交并建立可审查的合并关系，不通过改写历史解决。

基线只表示提纯正式开始，不表示 Core 已经完成或构建已经通过。

## 3. 单个子系统的提纯顺序

每次只处理一个明确的所有权范围：

1. 写清楚该子系统负责什么、不负责什么。
2. 列出最小公共表面和直接消费者。
3. 删除无消费者、无证据或越界的类型、目录和构建接线。
4. 建立最小构建目标，不依赖完整 Charm runtime。
5. 添加正例、负例和失败行为验证。
6. 记录保留、拒绝、延后和待重新组合的内容。

不得因为目录位置、代码数量或历史调用次数，直接认定某个概念属于 Core。

## 4. 最小证据

一个结果至少应提供：

- 独立构建命令和结果；
- 一个最小消费者；
- 必要的正例；
- 至少一个能证明边界的负例；
- 公共源码的依赖审计；
- 资源、错误和平台假设；
- 未验证项目和已知阻塞项。

没有证据的代码只能作为探索材料保留，不能作为完成结果。

## 5. 提交与分支规则

- 每个提交只表达一个清晰意图。
- 删除、契约调整、构建调整和验证尽量分开提交。
- 试验性改动未验证前可以不提交。
- OnlyCore 的结果不直接合并回旧主线。
- 需要回到主线时，只移植已验证的结果，并重新在主线环境验证。
- 关闭提纯分支前，为最终现场创建归档标签并保留裁决记录。

## 6. 停止条件

满足以下条件后，才可结束某个子系统的提纯：

- 边界和所有权已明确；
- 最小目标可以独立配置和构建；
- 公共表面不依赖无关子系统；
- 正例、负例和失败行为可重复；
- 未决事项已记录；
- 后续主线可以按记录重新采用结果。

未满足条件时，状态应标为进行中、延后或阻塞，不用“代码已经删得很少”作为完成依据。
