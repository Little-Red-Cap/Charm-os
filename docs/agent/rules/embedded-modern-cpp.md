# Embedded Modern C++ Rules

用途：
- 定义 Charm 在现代嵌入式 C++ 场景下的技术立场。
- 约束 AI 不得默认回退到传统 C/C++ 习惯。
- 要求接口、抽象与组织方式优先服务于语义正确、可验证、零成本抽象与长期演进。

适用场景：
- 讨论接口设计、抽象设计、类型系统建模
- 判断实现是否错误回退到传统写法
- 讨论是否采用更现代、更强类型方案
- 评估抽象是否符合零成本原则

不适用场景：
- 具体模块依赖/初始化/IO 纪律判断
- 单纯协作风格讨论

相关文件：
- `collaboration.md`
- `charm-architecture.md`

---

## 1. 项目定位

Charm 默认运行环境：

- Bare-metal 或最小化运行时
- 无动态内存分配依赖的路径
- 不依赖异常与 RTTI

默认约束包括：

- 资源受限
- 性能敏感
- 强调实时性、功耗与响应延迟

---

## 2. 技术立场

本项目不以以下目标为优先：

- C 兼容性
- ABI 稳定性
- 旧编译器支持
- “更多人能接受”

默认目标语义：

- 语义正确
- 可验证
- 零成本抽象
- 可长期演进

当“传统写法”与“现代强类型、可组合、可编译期建模写法”冲突时，优先后者。

---

## 3. 禁止项（默认视为设计失败）

- 动态内存分配：`new` / `delete` / `malloc` / `free`
- 异常
- RTTI
- 用宏承担语义职责
- 用运行期分支模拟编译期选择
- 协议层 busy-spin / 阻塞 / 自定义超时循环
- 协议层直接依赖 platform/hal/driver
- 手写入口初始化顺序

---

## 4. 强烈不推荐项

以下内容应尽量避免，使用时必须说明理由：

- `void*`
- 裸指针作为接口参数
- `.h/.cpp` 作为默认组织结构
- 依赖注释补足类型语义
- 依赖调用顺序或隐式约定传递语义

优先替代方式：

- 强类型
- 值语义句柄
- `std::span` / `std::array`
- `std::optional` / `std::expected`
- tag type
- `concept + template`
- `constexpr` / `consteval`

---

## 5. 接口与建模原则

### 5.1 类型系统优先

如果接口必须依赖文档才能安全使用，其类型设计大概率存在问题。

优先级：

1. 强类型
2. 值语义句柄
3. 标准容器视图
4. 显式可选与错误建模

### 5.2 Domain 优先

先建模“是什么”，再建模“怎么做”。

- 行为是 domain 的投影
- 数据结构先于算法
- 接口应表达语义，而非调用步骤

### 5.3 编译期优先

能在编译期解决的问题，不应拖到运行期。

鼓励：

- `constexpr` / `consteval`
- 类型级状态机
- 能力注入
- 编译期配置

---

## 6. 零成本抽象原则

任何抽象都应回答：

1. 增加多少 Flash 占用？
2. 增加多少 RAM 占用？
3. 增加多少运行期开销？
4. 编译器能否完全裁剪或优化？

无法解释成本的抽象，默认不引入。

---

## 7. 激进优先，但拒绝炫技

当“更现代但更激进”与“更传统但更熟悉”冲突时，默认优先现代方案。

但要区分：

- 激进：用类型系统表达更强约束
- 炫技：为了使用新特性而使用新特性

目标始终是：语义正确、可验证、零成本、可演进。

---

## 8. 逃生舱原则

允许有限妥协，但必须满足：

- 理由明确
- 范围最小化
- 边界隔离
- 标记清晰
- 有文档说明
- 可定期复审

合理理由通常仅限：

- 硬件强制约束
- 第三方 SDK 强制接口
- benchmark 证明的性能瓶颈

提出妥协方案时应说明：

- 为什么不能用规范方案
- 妥协范围多大
- 如何隔离
- 如何标记
- 是否可移除

---

## 9. 评审时的默认检查

- 是否引入动态分配
- 是否引入异常 / RTTI
- 是否用运行期分支替代编译期建模
- 是否用注释代替类型语义
- 是否引入不必要的异质接口
- 是否因“易懂”降低设计质量
