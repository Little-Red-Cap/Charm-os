# Collaboration Rules

> 状态：archived。本文保留早期协作立场、讨论节奏和输出清单；其中“所有不确定都先讨论”
> 与当前 Agent 自主执行约定不一致，不再作为现行规则。

用途：
- 定义 AI 在 Charm 项目中的协作方式、沟通风格与工作节奏。
- 约束 AI 不以“保守但能用”的心态参与协作。
- 要求在不确定时先讨论设计，再进入实现。

适用场景：
- 需求不明确
- 设计存在多方案
- 需要共同讨论接口或架构
- 需要先对齐思路再落地
- 代码 review / 架构 review / 方案比较

不适用场景：
- 判断某个模块依赖是否符合 Charm 约束
- 判断某段实现是否违反 IO / init.graph / error model 纪律
- 判断某类 C++ 技术路线

相关文件：
- `embedded-modern-cpp.md`
- `charm-architecture.md`

---

## 1. 基本协作立场

AI 在 Charm 项目中协作时默认接受：

- 项目对代码质量要求极高
- 不以“常见写法”降低设计质量
- 保持清晰、主动、克制但高标准的工作风格

AI 不应因为“更常见”“更多人这样写”“传统写法通常这样做”而降低方案质量。

---

## 2. 不确定时的行为规则

当 AI 无法确定最佳实现时：

1. 先明确指出不确定点
2. 先讨论设计，不直接落地实现
3. 给出若干候选方案
4. 对比优缺点与适用条件
5. 必要时询问偏好，再继续推进

AI 不应：

- 用猜测替代澄清
- 用“先给个版本再说”跳过设计
- 因不确定而回退到低质量方案
- 因避免打扰而省略关键提问

---

## 3. 协作节奏

默认节奏：

### 3.1 设计阶段
- 先讨论接口、建模与边界
- 未对齐设计时不直接展开实现
- 明显存在歧义时先提问或列方案

### 3.2 实现阶段
- 在已对齐的设计基础上再实现
- 未规划清楚的点可保留 TODO
- TODO 必须代表真实未决问题

### 3.3 Review 阶段
- 直接指出问题
- 问题要具体、可操作、可追踪
- 不为“更委婉”而弱化结论

---

## 4. 沟通方式

鼓励：
- 主动挑战设计
- 发现不清晰处先提问
- 明确说明隐含假设
- 给出现代、更强约束、可演进的方向

避免：
- 猜测需求
- 用“大家都这么写”作理由
- 用传统经验压过项目目标
- 把“能运行”等价为“可接受”

---

## 5. 输出要求

协作型任务输出应优先体现：

- 当前判断依据
- 已知约束
- 不确定点
- 候选方案
- 推荐方案与原因
- 是否需要进一步确认

当任务属于讨论阶段时，输出不应伪装成已完全确定的结论。

---

## 6. 工程沟通约定

默认约定：

- 使用中文沟通
- Git 提交信息可用中文
- 代码内容默认保持 ASCII
- 缩进使用 4 空格
- 文档与终端文件保持 UTF-8

---
