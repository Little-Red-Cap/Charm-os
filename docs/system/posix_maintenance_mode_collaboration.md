# POSIX 维护期协作策略

这份文档用于约定：在 `POSIX v0` 已收口之后，我们如何继续协作、如何判断是否该动 POSIX、以及动手时的默认节奏。

它不替代：

- `docs/system/posix_v0_closure_checklist.md`
- `docs/system/posix_stage_summary.md`
- `docs/system/posix_linux_compat_tasklist.md`
- `docs/system/posix_compat_roadmap.md`

它只回答一个更务实的问题：

> 进入维护模式后，什么情况该找 POSIX，什么情况先别动它，什么情况必须立刻处理？

---

## 1. 当前默认判断

当前默认前提是：

- `POSIX v0` 已收口；
- POSIX 不是当前仓库的主线扩张方向；
- 后续 POSIX 工作只应服务于真实阻塞点、真实回归、或验证链维护。

换句话说：

- 没有真实问题，就不主动开 POSIX 新战线；
- 没有契约漂移，就不重复补“看起来更完整”的兼容项；
- 没有验证链风险，就不随意改既有 smoke 路径。

---

## 2. 哪些情况应该找 POSIX

### A. 真实 blocker

典型触发：

- BusyBox 某个当前关注的 applet 被卡住；
- real-ELF 样例跑不起来；
- newlib / 公共 C surface 上的真实用户态程序被 POSIX 责任面卡住；
- shell / public C header / runtime bridge / QEMU 行为出现明显不一致。

这类问题应进入 POSIX 维护路径。

### B. 回归或契约漂移

典型触发：

- QEMU 主线 smoke 变红；
- newlib stdio 专项 smoke 变红；
- 已经承诺的 errno / fd / path / dir / process 语义出现回退；
- 头文件、实现、样例行为开始互相不一致。

这类问题优先级很高，应尽快处理。

### C. 验证链被上游变化打断

典型触发：

- CMake 组织调整导致 POSIX 目标、样例或 smoke 路径失效；
- 工具链变化导致 `-fmodules-ts`、交叉编译、QEMU 运行链出现新断点；
- 构建目录或脚本入口变化导致原有回归链不可用。

这类问题虽然不一定是 POSIX 语义问题，但会直接影响 POSIX 维护效率，因此也应该进入 POSIX 协同范围。

---

## 3. 哪些情况先不要动 POSIX

下面这些情况，默认不应主动开 POSIX 新工作：

- 只是“想让接口更像 Linux”
- 只是“想把 POSIX 面铺得更全”
- 某个冷门 flag / 冷门 errno / 冷门 applet 没有真实阻塞
- 想提前为未来 `fork`、完整 signal、动态链接、完整 `/proc` 预埋复杂模型
- 没有最小复现，但直觉上觉得“以后可能有用”

默认策略是：

- 能先不碰 POSIX，就先不碰；
- 能通过更上游的构建、样例、运行时组织解决，就不先往 POSIX 子系统里塞复杂度。

---

## 4. 问题分级与响应方式

### P0：立即处理

满足任一条件即进入 P0：

- QEMU 主线 smoke 失败
- newlib stdio 专项 smoke 失败
- 已收口主干能力发生明确回归
- 构建系统变化导致 POSIX 验证链完全断掉

处理方式：

- 先恢复验证链；
- 再恢复最小契约；
- 最后补文档和回归。

### P1：短周期处理

满足任一条件即进入 P1：

- BusyBox / real-ELF / newlib 样例被真实卡住；
- 公共 C surface 与 runtime 行为出现可复现漂移；
- 构建变化影响 POSIX 适配，但还有临时绕行路径。

处理方式：

- 先做最小复现；
- 再做最小修复；
- 最后决定是否需要提升为新基线 smoke。

### P2：观察与记录

满足任一条件可进入 P2：

- 某项能力未来可能会需要，但当前没有真实 blocker；
- 某些更宽接口面看起来有价值，但没有真实样例证明；
- 工具链或模块系统存在潜在风险，但当前未造成阻塞。

处理方式：

- 记录；
- 不主动扩张；
- 等真实触发后再升级。

---

## 5. 默认协作流程

后续每次要动 POSIX，默认按这条流程走：

1. **先分类**：这是 blocker、回归、还是验证链问题？
2. **先归属**：问题归 `fd_table` / `file` / `pipe` / `proc` / `term` / `env` / `errno` / `api` / 构建适配 的哪一层？
3. **先缩小**：给出最小复现，不直接在大样例上盲修。
4. **先修契约**：只修缺的那条最小语义，不顺手扩面。
5. **先补验证**：至少补一条最小 smoke 或样例回归。
6. **最后落文档**：同步到 stage summary / tasklist / roadmap / 对应设计文档。

如果一个改动不能完整走完这 6 步，默认不应直接并入主线。

---

## 6. 我们当前的分工建议

基于你接下来要推进 CMake 组织调整，当前最合适的分工是：

### 你这边

- 主导构建系统整理与组织重构；
- 决定新的目标命名、目录布局、构建入口；
- 处理不属于 POSIX 责任面的上游结构性变化。

### 我这边

- 负责 POSIX 维护态适配；
- 跟进 POSIX 目标、样例、QEMU smoke 路径的构建适配；
- 在上游变化后优先恢复 POSIX 验证链；
- 只在真实 blocker 出现时推进最小 POSIX 修复；
- 同步维护文档与回归口径。

这意味着：

- 我不主动把 POSIX 再拉回“功能扩张主线”；
- 但只要你的上游变化影响到 POSIX 路径，我就优先帮你把这条链接回去。

---

## 7. 以后每次提需求时，最省心的输入方式

为了让协作更高效，后续如果你要我介入 POSIX，最推荐直接给我下面四类信息之一：

### 方式 A：给 blocker

例如：

- 哪个 BusyBox applet 卡住了
- 哪个 ELF 样例失败了
- 哪个 newlib 程序编过但跑不通

### 方式 B：给回归

例如：

- 哪条 smoke 绿变红了
- 哪个 errno / fd / path 行为回退了

### 方式 C：给构建断点

例如：

- 哪个 target 没了
- 哪条 QEMU 路径断了
- 哪个 build dir / 脚本入口要适配

### 方式 D：给期望契约

例如：

- “这里我希望它像 `read(EOF) -> 0` 这样收敛”
- “这里我希望 `_isatty(non-tty)` 不改 errno”

只要输入能落到这四类之一，我就能比较快地把问题压缩成最小改动。

---

## 8. 当前维护期的优先顺序

在没有新 blocker 的情况下，优先顺序建议固定为：

1. 保住 QEMU 主线 smoke
2. 保住 newlib stdio 专项 smoke
3. 保住已收口 ABI 契约
4. 适配上游构建系统变化
5. 只在真实样例阻塞时补新缺口

这个顺序尽量不要反过来。

---

## 9. 一句话工作准则

POSIX 进入维护期之后，我们的默认工作准则应该是：

> 先守住验证链和已收口契约，再围绕真实 blocker 做小而稳的增量，而不是继续无边界扩张兼容面。
